# 任意分辨率视觉：图块打包与 NaFlex（Any-Resolution Vision: Patch-n'-Pack and NaFlex）

> 真实图像不是 224×224 的正方形。收据是 9:16，图表是 16:9，医学扫描可能是 4096×4096，手机截图是 9:19.5。2024 年之前 VLM 的答案——把所有图像缩放到固定正方形——丢掉了使 OCR、文档理解和高分辨率场景解析有效工作的信号。NaViT（Google，2023）证明了可以用块对角掩码将可变分辨率的图块打包进单个 Transformer 批次。Qwen2-VL 的 M-RoPE（2024）完全抛弃了绝对位置表。LLaVA-NeXT 的 AnyRes 将高分辨率图像平铺成基础图像加子图像。SigLIP 2 的 NaFlex 变体（2025）现在是希望用单个检查点服务所有宽高比的开放 VLM 的默认编码器。本章端到端实现图块打包。

**类型：** 构建  
**语言：** Python（标准库，图块打包器 + 块对角掩码）  
**前置知识：** Phase 12 · 01（ViT 图块）、Phase 12 · 05（LLaVA）  
**预计时间：** 约 120 分钟

## 学习目标

- 将一批可变分辨率图像的图块打包进单个序列，并构建块对角注意力掩码。
- 在 AnyRes 平铺（LLaVA-NeXT）、NaFlex（SigLIP 2）和 M-RoPE（Qwen2-VL）之间根据任务做出选择。
- 在不调整大小的情况下计算 OCR、图表和照片的 token 预算。
- 说出方形缩放的三种失败模式：文字挤压变形、内容裁剪丢失、填充浪费 token。

## 问题所在

Transformer 期望一个序列，批次是等长序列的堆叠。如果你的图像都是 224×224，每次都能得到 196 个图块 token，不需要填充，问题解决。在 224 上训练，在 224 上推理，不再需要考虑分辨率。

但现实不配合。文档是竖向的（8.5×11 英寸，约 2:3）。图表截图是横向的（16:9）。收据又高又细（1:3）。医学影像以 2048×2048 或更大尺寸输出。手机截图是 1170×2532（0.46:1）。

2024 年之前的三个选择及其失败原因：

1. 缩放到固定正方形（224×224 或 336×336）。挤压会扭曲文字和人脸。缩小会破坏图表标签和 OCR 内容。这是 LLaVA-1.5 之前的标准做法。
2. 裁剪到固定宽高比。你丢掉了大部分图像，选择裁剪位置本身就是一个视觉问题。
3. 填充到最长边。修复了扭曲，但对竖向图像来说有 50%+ 的 token 浪费在填充上，还有填充 token 的二次方注意力成本。

2024-2025 年的答案：让 Transformer 以原生分辨率吃图块，然后想办法将异质批次打包进单个序列，不浪费计算。

## 核心概念

### NaViT 与图块打包

NaViT（Dehghani 等，2023）是证明这在规模上可行的论文。想法是机械性的：

1. 对批次中的每张图像，在给定图块大小（比如 14）下计算其原生图块网格。
2. 将每张图像的图块展平为其自己的可变长度序列。
3. 将所有图像的图块拼接为批次的一个长序列。
4. 构建块对角注意力掩码，使图像 A 的图块只在图像 A 内部互相关注。
5. 携带每个图块的位置信息（2D RoPE 或分数位置嵌入）。

一批三张图像——336×336（576 token）、224×224（256 token）、448×336（768 token）——变成一个 1600-token 的序列，带有 1600×1600 的块对角掩码。没有填充，没有浪费计算，Transformer 处理任意宽高比。

NaViT 还在训练时引入了分数图块丢弃——在批次中随机丢弃 50% 的图块——既起到正则化效果，又加快了训练。SigLIP 2 继承了这一做法。

### AnyRes（LLaVA-NeXT）

LLaVA-NeXT 的 AnyRes 是务实的替代方案。给定一张高分辨率图像和一个固定编码器（336 分辨率的 CLIP 或 SigLIP），平铺图像：

1. 从预定义集合中选择最适合图像宽高比的网格布局——（1×1）、（1×2）、（2×1）、（1×3）、（3×1）、（2×2）等。
2. 将完整图像平铺为网格；每个平铺成为一张 336×336 的裁剪图。
3. 同时生成缩略图：将整张图像缩放到 336×336 作为全局上下文 token。
4. 将每个平铺送过冻结的 336-编码器，拼接平铺 token + 缩略图 token。

对于一张 672×672 的图像，2×2 网格加缩略图：4×576 + 576 = 2880 个视觉 token。代价高昂但有效——LLM 同时看到局部细节和全局上下文。

当你的编码器是冻结的且只支持一种分辨率时，AnyRes 是首选。但对于大图像，它会爆炸式增加 token 数（1344×1344 的图像在 4×4 网格下约 9216+576≈9800 个 token，填满了大多数 8k LLM 上下文的全部空间）。

### M-RoPE（Qwen2-VL）

Qwen2-VL 引入了多模态旋转位置编码。不同于 NaViT 的分数位置或 AnyRes 的平铺加缩略图，每个图块携带一个三维位置（时间、高度、宽度）。查询/键的旋转以正确的频率处理任意 H、W 和时间长度。

M-RoPE 无需重训就能原生支持动态分辨率。推理时你送入任意 H×W 的图像，图块嵌入器产生 H/14×W/14 个 token，每个 token 获得其 (t=0, r=行, c=列) 位置，RoPE 以正确频率旋转注意力，完成。Qwen2.5-VL 和 Qwen3-VL 延续了这一方案。InternVL3 的 V2PE 是每种模态采用可变编码的相同思路。

与 AnyRes 不同，M-RoPE 在原生分辨率下是 O(H×W/P²) 个 token——没有乘法平铺开销。与 NaViT 不同，它仍然期望每次前向传播一张图像。跨分辨率的批处理仍然需要在其上加图块打包。

### NaFlex（SigLIP 2）

NaFlex 是 SigLIP 2 检查点的原生灵活模式。单个模型在推理时支持多种序列长度（256、729、1024 个 token）。内部在训练时使用 NaViT 风格的图块打包，每个图块使用绝对分数位置。卖点：一个检查点，根据任务在推理时选择 token 预算。

语义任务（分类、检索）用 256 个 token；OCR 或图表理解用 1024 个 token；无需重训。

### 打包掩码

块对角掩码是大多数实现出问题的地方。对于覆盖图像 `i=0..B-1`（长度为 `n_i`）、总长度为 `N_total` 的打包序列，形状为 `(N_total, N_total)` 的掩码 `M` 在两个索引落在同一张图像的块内时为 1，否则为 0。你可以从累积长度列表构建：

```
offsets = [0, n_0, n_0+n_1, ..., N_total]
M[i, j] = 1 iff there exists b where offsets[b] <= i < offsets[b+1] and offsets[b] <= j < offsets[b+1]
```

在 PyTorch 中可以用 `torch.block_diag` 或显式 gather 一行实现。FlashAttention 的可变长度路径（`cu_seqlens`）完全跳过掩码，直接用累积长度张量在序列内部做注意力——对典型批次来说比密集掩码快约 10 倍。

### Token 预算

按任务选择策略：

- OCR / 文档：1024-4096 个 token。SigLIP 2 NaFlex 1024，或 AnyRes 3×3 + 缩略图。
- 图表和 UI：原生 384-448 分辨率的 729-1024 个 token。Qwen2.5-VL 动态分辨率加最大像素上限。
- 自然照片：256-576 个 token 足够，下游 LLM 看到的信息已充分。在内容密度高的地方多付 token。
- 视频：空间池化后每帧 64-128 个 token，2-8 FPS。Lesson 12.17 详细介绍。

2026 年的生产规则：根据任务设定每任务最大像素上限，以原生宽高比编码到该上限，打包批次，跳过填充。Qwen2.5-VL 为此暴露了 `min_pixels` 和 `max_pixels` 两个旋钮。

## 动手使用

`code/main.py` 为一批异质图像（使用整数像素坐标）实现图块打包。它：

- 接受一组（H、W）图像尺寸。
- 在图块大小 14 下计算每张图像的图块序列长度。
- 将它们打包进总长度为 `sum(n_i)` 的单个序列。
- 构建块对角注意力掩码（密集形式，以便清晰展示）。
- 比较打包成本与方形缩放和 AnyRes 平铺的对比。
- 打印一张混合批次（收据、图表、截图、照片）的 token 预算表。

运行它。输出的数字就是为什么 2026 年每个开放 VLM 都使用图块打包的原因。

## 输出产物

本章生成 `outputs/skill-resolution-budget-planner.md`。给定混合宽高比工作负载（OCR、图表、照片、视频帧）和总 token 预算，它选择正确的策略（NaFlex、AnyRes、M-RoPE 或固定正方形），并输出每个请求的配置。在为产品设计 VLM 时使用这个技能——它能防止静默的 10 倍 token 膨胀搞垮延迟预算。

## 练习

1. 一张收据是 600×1500（1:2.5）。在图块大小 14 下有多少原生分辨率 token？缩放到 336 的正方形后有多少？在实践中哪种方式损失更多 OCR 准确率？

2. 为四张长度分别为 256、576、729、1024 的图像构建块对角掩码。验证注意力矩阵为 2585×2585，非零元素恰好为 `256² + 576² + 729² + 1024²` 个。

3. 对一张 1792×896 的图像在图块 14 下比较：（a）方形缩放到 336 后编码；（b）AnyRes 2×1 + 缩略图；（c）M-RoPE 原生分辨率。哪种使用 token 最少？哪种保留细节最多？

4. 实现分数图块丢弃：给定一个打包序列，随机均匀丢弃 50% 的 token，并相应更新块对角掩码。测量掩码稀疏度的变化。

5. 阅读 Qwen2-VL 论文（arXiv:2409.12191）第 3.2 节。用两句话描述 `min_pixels` 和 `max_pixels` 控制什么，以及为什么两个边界都重要。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| 图块打包（Patch-n'-pack） | "NaViT 风格打包" | 将不同图像的可变长度图块序列拼接到一个批次维度中。 |
| 块对角掩码（Block-diagonal mask） | "打包掩码" | 限制每张图像的图块只关注自身、不关注打包邻居的注意力掩码。 |
| AnyRes | "LLaVA-NeXT 平铺" | 将高分辨率图像分割为固定大小平铺的网格加全局缩略图；用固定编码器编码每个平铺。 |
| NaFlex | "SigLIP 2 原生灵活" | 单个 SigLIP 2 检查点，推理时无需重训即可服务 256/729/1024-token 预算。 |
| M-RoPE | "多模态 RoPE" | 无需位置表即可处理任意 H、W、T 的三维旋转位置编码（时间、行、列）。 |
| cu_seqlens | "FlashAttention 打包" | FlashAttention varlen 路径使用的累积长度张量，替代密集块对角掩码。 |
| min_pixels / max_pixels | "分辨率边界" | Qwen2.5-VL 限制极小或极大输入 token 数量的每请求旋钮。 |
| 视觉 token 预算（Visual token budget） | "每图像 token 数" | 每张图像发出的图块 token 的大致数量；决定 LLM 的提示词预算和注意力成本。 |
