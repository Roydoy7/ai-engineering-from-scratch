# 全模态模型：Qwen2.5-Omni 与思考者-说话者分离（Omni Models: Qwen2.5-Omni and the Thinker-Talker Split）

> GPT-4o 2024 年 5 月的产品演示之所以具有颠覆性，不是因为底层模型，而是因为产品形态——一个语音界面：你说话，模型看到摄像头看到的，然后在 250ms 内说话回应。开源生态在 2024 年和 2025 年余下的时间都在竞相达到这一产品形态。Qwen2.5-Omni（2025 年 3 月）是参考开放设计：一个思考者（大型文本生成 Transformer）加上一个说话者（并行语音生成 Transformer），通过流式语音 token 相连。Mini-Omni 将其简化，Moshi 匹配了其延迟，GLM-4-Voice 将其扩展到中文。本章解读思考者-说话者架构以及让流式实时对话成为可能的延迟预算。

**类型：** 构建  
**语言：** Python（标准库，流式流水线延迟模拟器 + VAD 循环）  
**前置知识：** Phase 12 · 19（音频-LLM）、Phase 12 · 16（任意到任意）  
**预计时间：** 约 180 分钟

## 学习目标

- 将推理流水线分为思考者（文本推理）和说话者（语音合成），解释为什么并行流式传输有效。
- 逐组件计算对话交互的首字节音频时间（TTFAB）预算。
- 描述 TMRoPE 如何在思考者内部跨视觉、音频和文本进行时间对齐的位置编码。
- 说出三种实时对话模式：半双工、轮换、全双工。

## 问题所在

实时语音助手需要快速完成很多事情：

1. **听用户说话。** 实时语音分词，语音活动检测（VAD）以知道用户何时说完。
2. **可选地看。** 摄像头以 2-4 FPS 输入，与音频一起流式传送给思考者。
3. **思考。** 基于对话历史组合回复。
4. **说话。** 合成音频 token，解码为波形，流式传送到用户扬声器。

每一步都增加延迟。对话感要求总往返时间 < 500ms——低于此值，用户不再注意到延迟。GPT-4o 声称约 250ms。Moshi 约 160ms。Qwen2.5-Omni 约 350-500ms。

每个组件都需要流式处理。不能"先批量处理所有内容再解码"。

## 核心概念

### 思考者与说话者

Qwen2.5-Omni 的分解：

- **思考者：** 70 亿-800 亿参数的文本生成 Transformer。消耗交错的文本 + 图像 + 音频 token。输出代表要说什么的文本 token。
- **说话者：** 一个较小的语音生成 Transformer（2 亿-10 亿参数）。消耗思考者的文本输出 token 加上最近的语音上下文 token。输出离散语音 token（残差 VQ 索引）。
- **语音解码器：** 实时将语音 token 转换为音频样本的流式波形解码器（SNAC、MoVQGAN 家族）。

分离很重要。思考者需要足够大以实现良好推理。说话者可以很小，因为它的任务是局部的——将文本转换为语音 token。更大的说话者并不更有表现力，只是更慢。

并行运行两者的方式：

1. 思考者输出文本 token t_i。
2. 说话者消耗 t_i（通过流式传输）并输出语音 token s_i、s_{i+1}、……、s_{i+k}。
3. 语音解码器在语音 token 到来时消耗并输出音频样本。
4. 当思考者到达文本 token t_{i+3} 时，说话者已经流式传输了 t_0..t_{i+2} 的音频。

### TMRoPE——时间对齐的多模态位置

思考者需要整合图像帧（比如以 4 FPS 到来）、音频帧（以 50 帧/秒到来）和对话历史中的文本。朴素的序列顺序（所有图像，然后所有音频，然后文本）会丢失时间对齐。

TMRoPE 为每个 token 分配绝对时间戳。t=2.3s 的视觉 token，t=2.32s 的音频 token，用户在 t=2.35s 说的"停"。RoPE 按时间戳旋转注意力；模型将它们视为时间上同时发生的。

这是让"他一边挥手一边说你好"能够正确工作的基础设施——模型在同一个概念时刻看到视频帧和音频。

### 流式语音合成

语音 token 必须流式传输。Mini-Omni（Xie & Wu，2024）引入了"语言模型可以在流式思考的同时听和说"：思考者输出 token 和说话者输出 token 在同一序列中交错。说话者在思考者提交下一个文本 token 时立即开火。没有批次边界。

Moshi（Défossez 等，2024 年 10 月）是最快的开源实现。单 A100 上 TTFAB 为 160ms。架构：一个 70 亿参数的 Transformer 在交替位置上输出文本和语音 token，带有将思考流与说话流分离的"内心独白"。这实际上是思考者 + 说话者融合成一个模型的精心训练。

### VAD 与轮换

语音活动检测在输入侧运行。两种模式：

- **半双工：** 用户说话，模型听。模型说话，用户听。通过 VAD 静默检测（约 200ms）实现清晰的切换。
- **全双工：** 两者可以同时说话。模型可以发出反馈信号（"嗯嗯"）或打断。难度大得多。Moshi 支持此功能。

Qwen2.5-Omni 默认支持半双工，通过静默阈值实现轮换。全双工需要应用层处理。

### Qwen3-Omni（2025 年 11 月）

继任者。Qwen3-80B 思考者，更大的说话者，改进的 TMRoPE-v2。延迟接近 GPT-4o 的 250ms。开放权重。OmniBench 基准与 Gemini 2.0 Live 竞争。

### 生产延迟预算

典型流式交互的延迟：

- 麦克风 → 音频 token：40-80ms。
- 预填充（提示词 + 历史）：7B 时 100-200ms，70B 时多得多。
- 第一个思考者文本 token：40ms。
- 说话者处理第一个文本 token：20ms。
- 第一批语音 token 提交：40ms。
- 残差 VQ 解码：30ms。
- 语音波形解码：50-80ms。

**TTFAB 总计：** 7B 时 320-510ms，70B 时 600-900ms。前沿质量通常意味着 70B+；因此前沿延迟差距的由来。

### Token 率数学

以 16kHz 语音、50 Hz 基础语音 token 计，每秒输出音频需要 50 个语音 token。说话者必须以 ≥50 tok/s 的速度输出才能跟上。在 H100 上典型 LLM 吞吐量为 30-80 tok/s，一个小型（2 亿-3 亿参数）说话者足够快；7B 的说话者会跟不上。

这就是为什么存在专用的小型说话者模型，而不是"直接用主模型"。

## 练习

1. 目标 TTFAB 为 300ms。使用 7B 思考者和 3 亿参数说话者，写出每个组件的延迟。

2. Qwen2.5-Omni 使用 TMRoPE。描述当用户在 t=1s 开始说话、摄像头在 t=1.2s 捕捉到手势时，模型看到的提示词是什么样子。

3. 全双工支持要求模型在听的同时输出音频。提出一种教授此能力的训练数据格式。

4. 阅读 Moshi 论文第 4 节。描述"内心独白"分离，以及为什么它避免了思考者-说话者的分裂。

5. 计算吞吐量预算：说话者必须以多快的速度输出 token 才能跟上 16kHz 语音的 50 基础层 token/秒？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| 思考者（Thinker） | "推理大脑" | 产生要说什么的大型文本生成 Transformer。 |
| 说话者（Talker） | "语音生成口" | 从思考者文本产生离散语音 token 的小型 Transformer。 |
| TTFAB | "延迟预算" | 首字节音频时间：从用户说话结束到第一个音频样本输出。 |
| TMRoPE | "时间对齐 RoPE" | 跨视觉、音频、文本使用绝对时间戳的位置编码。 |
| 半双工（Half-duplex） | "轮换" | 用户和模型交替；VAD 静默检测用户说完。 |
| 全双工（Full-duplex） | "同时" | 模型可以同时说话和听；支持反馈信号。 |
| 内心独白（Inner monologue） | "Moshi 分离" | 单模型设计，思考流和说话流在其中交错。 |
