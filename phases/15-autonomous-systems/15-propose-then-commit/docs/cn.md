# 人机循环：提议-再-提交（Human-in-the-Loop: Propose-Then-Commit）

> 2026 年对 HITL 的共识是具体的。它不是"智能体询问，用户点击批准"。而是提议-再-提交：提议的动作以幂等键持久化到耐久存储；向审查者展示意图、数据血统、权限触及范围、爆炸半径和回滚计划；只有在明确确认后才提交；执行后验证以确认副作用确实发生。LangGraph 的 `interrupt()` 加 PostgreSQL 检查点、Microsoft Agent Framework 的 `RequestInfoEvent` 和 Cloudflare 的 `waitForApproval()` 都实现了相同的形状。典型失败模式是橡皮章批准："批准？"在未审查的情况下被点击。有据可查的缓解是带明确清单的挑战-响应机制。

**类型：** 学习  
**语言：** Python（标准库，带幂等性的提议-再-提交状态机）  
**前置知识：** Phase 15 · 12（持久执行）、Phase 15 · 14（触发器）  
**预计时间：** 约 60 分钟

## 问题所在

智能体采取一个动作。用户必须决定：批准还是不批准。如果决定是即时的，那它很可能不是真正的审查。如果决定是结构化的，那它慢但可信赖。工程问题是如何让结构化审查成为阻力最小的路径。

2023 年代的 HITL 模式是同步提示："智能体想向 X 发送正文为 Y 的邮件——批准？"用户点击批准。每个人都感觉系统是安全的。在实践中，这个界面被大量橡皮章盖章：用户快速批准，批准几乎不能预测什么，当智能体出错时，审计轨迹显示一长串用户不记得的批准历史。

2026 年模式——提议-再-提交——将 HITL 移到耐久基底上，附加结构化元数据，并要求明确提交。每个托管智能体 SDK 都提供一个版本：LangGraph `interrupt()`、Microsoft Agent Framework `RequestInfoEvent`、Cloudflare `waitForApproval()`。API 名称不同；形状相同。

## 核心概念

### 提议-再-提交状态机

1. **提议（Propose）。** 智能体产生提议的动作。持久化到耐久存储（PostgreSQL、Redis、Durable Object）。包括：
   - 意图（智能体为什么要这样做）
   - 数据血统（什么来源导致了这个提议）
   - 权限触及范围（哪些范围/文件/端点）
   - 爆炸半径（最坏情况是什么）
   - 回滚计划（如果提交了，如何撤销）
   - 幂等键（每个提议唯一；重新提交返回相同记录）
2. **展示（Surface）。** 审查者查看带所有元数据的提议。审查者是人（不是智能体自我审查）。
3. **提交（Commit）。** 明确确认。动作执行。
4. **验证（Verify）。** 执行后，读回副作用并确认。如果验证步骤失败，系统处于已知不良状态，警报启动。

### 幂等键

没有幂等键，瞬态失败后的重试可能双重执行一个已批准的动作。具体示例：用户批准"从 A 向 B 转账 $100"。网络抖动。工作流重试。用户只批准了一次，但转账执行了两次。幂等键将批准绑定到单个唯一副作用；第二次执行是空操作。

这与 Stripe 和 AWS API 使用的幂等性模式相同。将其重用于智能体批准在 Microsoft Agent Framework 文档中有明确说明。

### 耐久性：为什么批准比进程存活更久

批准等待区是智能体不拥有的状态。工作流已暂停（第 12 课）。当批准到达时，工作流从该点精确恢复。这就是为什么 LangGraph 将 `interrupt()` 与 PostgreSQL 检查点配对，而不仅仅是内存状态——两天后到达的批准仍然能找到完整的工作流。

### 橡皮章批准与挑战-响应缓解

HITL 的默认 UI（"批准"/"拒绝"按钮）产生没有真正审查的快速批准。有据可查的缓解：挑战-响应清单，要求在启用"批准"按钮之前对特定问题给出明确肯定回答。具体形式：

- "你是否理解这触及的资源？[ ]"
- "你是否验证了爆炸半径是可接受的？[ ]"
- "如果失败，你是否有回滚计划？[ ]"

这不是为了官僚主义而设的——而是强制机制。无法勾选选项的审查者要么请求澄清（升级），要么拒绝（安全默认）。Anthropic 智能体安全研究明确将清单驱动的 HITL 引用为橡皮章批准模式的缓解措施。

### 什么算作后果性动作

并非每个动作都需要提议-再-提交。2026 年指导：

- **后果性动作**（始终 HITL）：不可逆写入、金融交易、对外通信、生产数据库更改、破坏性文件系统操作。
- **可逆动作**（有时 HITL）：本地文件编辑、暂存环境更改、带明确回滚的可逆写入。
- **读取和检查**（从不 HITL）：读取文件、列出资源、调用只读 API。

### 执行后验证

"提交运行了"不等于"副作用发生了"。网络分区和竞态条件可能产生一个认为自己成功了但后端没有持久化的工作流。验证步骤在提交后重新读取目标资源以确认。这与带 `RETURNING` 子句的数据库事务或 AWS `PutObject` 后的 `GetObject` 是相同的模式。

### EU AI Act 第 14 条

第 14 条要求对欧盟高风险 AI 系统进行有效的人类监督。"有效"不是装饰性的。监管语言明确排除橡皮章模式。带挑战-响应的提议-再-提交是在 Microsoft 智能体治理工具包合规文档中能通过第 14 条审查的形式。

## 使用它

`code/main.py` 在标准库 Python 中实现提议-再-提交状态机。耐久存储是 JSON 文件。幂等键是 (thread_id, action_signature) 的哈希。驱动程序模拟三种情况：干净的批准流、瞬态失败后的重试（不得双重执行），以及橡皮章默认与挑战-响应流。

## 交付它

`outputs/skill-hitl-design.md` 审查提议的 HITL 工作流的提议-再-提交形状，并标记缺失的元数据、幂等性、验证或挑战-响应层。

## 练习

1. 运行 `code/main.py`。确认已批准提议的重试使用耐久记录且不重新执行。现在将幂等键更改为包含时间戳，并显示重试双重执行。

2. 用 `rollback` 字段扩展提议记录。模拟验证步骤失败的执行。显示回滚自动触发。

3. 阅读 Microsoft Agent Framework 的 `RequestInfoEvent` 文档。识别 API 包含而玩具引擎缺少的一个元数据字段。添加它并解释它能防范什么。

4. 为特定动作（如"发布到公共 Twitter 账户"）设计挑战-响应清单。审查者必须回答的三个问题是什么？为什么是这三个？

5. 选择一个同步"批准？"提示就足够的情况（不需要耐久存储）。解释原因，并命名你接受的风险类别。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Propose-then-commit（提议-再-提交） | "两阶段批准" | 持久化提议 + 明确提交 + 验证 |
| Idempotency key（幂等键） | "重试安全 token" | 每个提议唯一；第二次执行为空操作 |
| Data lineage（数据血统） | "来源" | 导致提议的特定来源内容 |
| Blast radius（爆炸半径） | "最坏情况" | 动作出错时的影响范围 |
| Rubber-stamp（橡皮章） | "快速批准" | 在未真正审查的情况下点击"批准" |
| Challenge-and-response（挑战-响应） | "强制清单" | 审查者必须明确确认特定问题 |
| RequestInfoEvent | "MS 智能体框架原语" | 带结构化元数据的耐久 HITL 请求 |
| `interrupt()` / `waitForApproval()` | "框架原语" | LangGraph/Cloudflare 相同形状的等价物 |
