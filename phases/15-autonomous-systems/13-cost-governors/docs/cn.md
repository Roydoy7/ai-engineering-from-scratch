# 行动预算、迭代上限与成本控制器（Action Budgets, Iteration Caps, and Cost Governors）

> 生产长时域智能体的默认失败模式不是灾难性的——而是悄无声息地、昂贵地循环。每个无上限的 LLM 调用都是一次潜在的无限循环。Anthropic 的 Claude Code 暴露了 `max_turns` 和 `max_budget_usd`；两者都没有被大多数部署设置。OpenAI Assistants 和 LangGraph 有等价的旋钮。Microsoft 智能体治理工具包（2026 年 4 月 2 日）将它们与 OWASP Agentic Top 10 和 EU AI Act 第 14 条一同编目。一个 12 层的成本控制器栈覆盖了独立失败的不同时间尺度。没有一个单一的上限能做到所有这些——你需要全部层次。

**类型：** 学习  
**语言：** Python（标准库，分层成本控制器模拟器）  
**前置知识：** Phase 15 · 10（权限模式）、Phase 15 · 01（长时域智能体）  
**预计时间：** 约 45 分钟

## 问题所在

一个生产编码智能体被要求修复一个 bug。它进入一个循环：读取文件、调用 LLM、写入补丁、运行测试、失败、再次调用 LLM。在八小时内它调用了 LLM 1,400 次，花费了 $340，什么都没有修复。没有人注意到，因为没有警报，没有上限，没有预算门控。

这是"Denial of Wallet"（钱包拒绝服务）失败模式：智能体没有受损，没有越权——它只是在不应该继续的时候不断消费。它与 DDoS 共享形状，但由内部循环而非外部攻击者驱动。

从预算控制故障的真实案例：一个团队部署了一个新的"订单跟踪"技能。技能运行良好——对于简单查询。但对于模糊请求，它进入一个工具调用循环来缩小范围。每个循环多花 $0.40。月度成本从 $1,200 跳到 $4,800，没有任何配置更改，没有任何警报触发，因为没有人设置阈值。

## 核心概念

### 12 层成本控制器栈

没有单一上限能捕获所有失败模式。不同的层运行在不同的时间尺度上，捕获不同的失败类：

| 层 | 机制 | 捕获什么 |
|----|------|---------|
| 1 | 每请求 `max_tokens` | 单个 LLM 调用的失控输出 |
| 2 | 每任务 token 预算 | 跨轮次的 token 累积 |
| 3 | 每任务美元预算（`max_budget_usd`） | 混合模型会话中的成本 |
| 4 | 每工具调用上限 | 一次工具调用中的无限工具使用 |
| 5 | 迭代上限（`max_turns`） | 不进展的循环 |
| 6 | 滚动时间窗口上限 | 低速多会话泄漏 |
| 7 | 财务速度限制（如 $50/10 分钟） | 爆发性的失控花费 |
| 8 | 分级模型路由 | 昂贵模型处理简单请求 |
| 9 | 提示词缓存 | 可缓存的重复上下文重新计算 |
| 10 | 上下文窗口化 | 不必要的长上下文传递 |
| 11 | 高价动作上的 HITL 检查点 | 高成本单步越过预算 |
| 12 | 违规时的断路器/终止开关 | 一切都失败时的最后防线 |

### 为什么是栈而非单一上限

每一层捕获其他层会遗漏的内容：

- **失控循环**：`max_turns` 在 N 步内捕获，但对于每次调用 $0.001 的慢泄漏，在日限触发之前 `max_turns` 会多次击中。
- **慢泄漏**：财务速度限制捕获爆发；月度上限捕获低速泄漏；两者都不能替代另一个。
- **糟糕发布**：日和月上限捕获在截止日期后才出现的模式；`max_turns` 在首次运行时就关闭了它。

类比：TCP/IP 有每包校验和、每段超时和端到端确认。每一层捕获其他层遗漏的错误。成本控制器栈出于同样的原因有层次。

### Claude Code 预算表面

Claude Code 暴露了三个主要旋钮：

```python
# Claude Code SDK — 预算控制
result = agent.run(
    task="fix the login bug",
    max_turns=20,                    # 层 5：迭代上限
    max_budget_usd=5.00,            # 层 3：每任务美元预算
    allowed_tools=["Read", "Edit"],  # 层 4 的前身：工具允许列表
    disallowed_tools=["Bash"],       # 排除高风险工具
)
```

`max_turns` 是明确的迭代上限——第 10 课的自动模式有每工具配置以进一步细化它。`max_budget_usd` 在 LLM API 调用通过中间层时追踪美元支出。两者都不是默认设置的——你必须在每次调用时或在全局配置中明确设置它们。

### 财务速度限制

速度限制是成本控制器栈中最常被忽略的层。结构：

- 追踪滚动时间窗口内的支出（如最近 10 分钟）。
- 如果支出超过阈值（如 $50/10 分钟），则暂停或终止所有会话。
- 在新时间窗口开始时重置。

为什么速度很重要：一个在下午 2:00 进入循环的任务可以在 `max_budget_usd` 基于每任务的检测到它之前，在 3:00 燃烧掉每月预算的 30%。速度限制捕获"支出太快"，而不仅仅是"支出太多"。

### $1,200 → $4,800 真实案例

时间线：

1. 团队部署了"订单跟踪"技能，经过了有限的负载测试。
2. 技能在明确的订单号上运行良好；在模糊查询上它调用多个工具来缩小范围。
3. 缺少每工具调用上限和每任务美元预算。
4. 第一个月：一些模糊查询，但量小。第二个月：更高的量，每个有问题查询的工具调用循环，没有警报触发。
5. 月底审查：成本从 $1,200 跳到 $4,800。没有行为上的"失败"——智能体在做它被要求做的事。没有预算门控告诉它停止。

修复：每工具调用上限（每任务 3 个工具调用）+ 每任务 $0.50 美元上限 + 超过 $100/小时时的速度警报。成本回落到 $1,400。

### Microsoft 智能体治理工具包

Microsoft 智能体治理工具包（2026 年 4 月 2 日）将预算控制编目为两个外部框架下的合规要求：

- **OWASP Agentic Top 10**：将"无限资源消耗"列为前 3 名风险。成本控制器直接映射到缓解措施。
- **EU AI Act 第 14 条**：要求"人工监督"措施。HITL 检查点（第 11 层）和终止开关（第 12 层）是技术符合性的。

工具包的相关性：它将最佳实践代码化为可审计的检查表。如果你在受监管行业部署生产智能体，预计审核员会询问每一层。

### 何时层次不够

- 有界循环被另一个系统的缺陷触发（LLM 调用失败 → 重试逻辑触发更多 LLM 调用 → 速度触发暂停 → 重试逻辑再次绕过暂停）。
- 成本追踪本身失败（追踪器宕机；层 3-7 盲目运行）。
- 财务阈值设置得太高，无法捕获渐进的漂移。

缓解：追踪器监控（你的追踪器有心跳吗？）和阈值审查（为什么是 $50/10 分钟而不是 $10/10 分钟？）。

## 练习

1. 运行 `code/main.py`。将财务速度限制从 $50/10 分钟更改为 $10/10 分钟。工具调用循环何时被捕获？是在 `max_turns` 之前还是之后？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Denial of Wallet（钱包拒绝服务） | "花钱攻击" | 智能体在不失败的情况下无限消耗预算；内部循环而非外部攻击 |
| `max_turns` | "步骤上限" | 每个智能体会话的最大迭代次数 |
| `max_budget_usd` | "美元上限" | 会话的最大美元支出；超过时中止 |
| Financial velocity limit（财务速度限制） | "每分钟支出上限" | 滚动时间窗口阈值；捕获爆发性循环 |
| Kill switch（终止开关） | "紧急停止" | 超过阈值时立即终止所有会话的断路器 |
| HITL checkpoint（HITL 检查点） | "人类审查门" | 高价动作上暂停并等待批准的点 |
| Tiered routing（分级路由） | "使用更便宜的模型" | 将简单请求路由到更便宜的模型以降低成本 |
| Cost-governor stack（成本控制器栈） | "分层预算控制" | 在不同时间尺度捕获不同失败模式的 12 层 |
