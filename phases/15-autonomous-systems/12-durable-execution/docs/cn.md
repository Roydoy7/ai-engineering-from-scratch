# 长时运行后台智能体：持久执行（Long-Running Background Agents: Durable Execution）

> 生产长时域智能体不运行在 `while True` 中。每个 LLM 调用成为一个带检查点、重试和重放的活动。Temporal 的 OpenAI Agents SDK 集成于 2026 年 3 月 GA。Claude Code Routines（Anthropic）无需持久本地进程地运行预定的 Claude Code 调用。会话在人类输入时暂停，在部署中存活，并从由 `thread_id` 键控的最新检查点恢复。新人机工程学背后是一个旧模式——工作流编排——带一个新输入：LLM 调用作为必须在恢复时确定性重放的非确定性活动。

**类型：** 学习  
**语言：** Python（标准库，最小持久执行状态机）  
**前置知识：** Phase 15 · 10（权限模式）、Phase 15 · 01（长时域智能体）  
**预计时间：** 约 60 分钟

## 问题所在

考虑一个运行四小时的智能体。它调用三个工具，两次提示用户，并发出四十个 LLM 调用。中途，它运行的主机重启了。会发生什么？

- 在朴素的 `while True` 循环中：一切都丢失了。运行从头开始。三个工具调用（带真实副作用）再次执行。用户再次被提示他们已经批准的事情。四十个 LLM 调用被重新计费。
- 有持久执行：运行从最近的检查点恢复。已完成的活动不会重新执行；它们的结果从持久日志中重放。用户不会重新批准他们已经批准的事情。已经发出的 LLM 调用不会重新计费。

这与工作流引擎已经提供了十年的相同模式（Temporal、Cadence、Uber 的 Cherami）。新的是 LLM 调用现在是一种活动——非确定性、昂贵、有副作用——它们与这个模式完美契合。

本课的主线：长时域可靠性衰减（METR 观察到"35 分钟退化"——成功率随时域大致二次方下降）。持久执行使运行能够超过可靠性配置文件支持的时间，如果设计正确，这是一种新的安全失败方式；如果设计错误，则是不安全的。

## 核心概念

### 活动、工作流和重放

- **工作流**：确定性编排代码。定义活动序列、分支、等待。必须是确定性的，以便可以从事件日志重放而不出现令人惊讶的发散。
- **活动**：非确定性、可能失败的工作单元。LLM 调用、工具调用、文件写入、HTTP 请求。每个活动都记录其输入和（完成后）其输出。
- **事件日志**：持久的后备存储。每个活动开始、完成、失败、重试和每个工作流决策都被记录。
- **重放**：在恢复时，工作流代码从头重新运行；每个已经完成的活动返回其记录的结果而不重新执行。只有尚未完成的活动才实际运行。

这与 React 针对虚拟 DOM 重新渲染，或 Git 从提交重建工作树的形状相同。编排器中的确定性是使持久性廉价的原因。

### 为什么 LLM 调用符合这个模式

LLM 调用是：
- 非确定性的（temperature > 0；即使 temperature 0 也会在模型版本之间漂移）。
- 昂贵的（金钱和延迟）。
- 可能失败的（速率限制、超时）。
- 有副作用的（如果它们调用工具）。

这正是活动配置文件。将每个 LLM 调用包装为活动可以提供带指数退避的重试、跨重启的检查点，以及用于调试的可重放追踪。

### 由 `thread_id` 键控的检查点

LangGraph、Microsoft Agent Framework、Cloudflare Durable Objects 和 Claude Code Routines 都收敛到同一个 API 形状：`thread_id`（或等价物）标识会话；每个状态转换持久化到后端（PostgreSQL 默认，开发用 SQLite，缓存用 Redis）；恢复读取最新检查点。

后端选择很重要：

- **PostgreSQL**：持久、可查询、在部署中存活。LangGraph 的默认。
- **SQLite**：仅本地开发；跨主机丢失数据。
- **Redis**：快速但临时，除非配置了 AOF/快照。
- **Cloudflare Durable Objects**：透明分布；按唯一键范围界定；存活数小时到数周。

### 人类输入作为一等状态

提案再提交（第 15 课）需要持久的"等待人类"状态。工作流暂停，外部队列保持待处理请求，批准从该点精确恢复。没有持久性，这是尽力而为；有了它，隔夜批准到达，工作流早上继续。

### 35 分钟退化

METR 观察到测量的每个智能体类别在连续操作约 35 分钟后都显示可靠性衰减。任务持续时间翻倍大致使失败率变为四倍。持久执行不能修复这个问题；它让你运行超过可靠性配置文件支持的时间。安全模式是将持久性与需要在重新进入时新鲜 HITL 的检查点，以及限制总计算量的预算停止开关（第 13 课）结合使用，无论挂钟时间如何。

### 持久执行何时是错误答案

- 没有人类输入的几分钟内的运行。开销 > 收益。
- 严格只读的信息检索。
- 正确性需要在一个上下文窗口内端到端的任务（某些推理任务；某些一次性生成）。

## 使用它

`code/main.py` 在标准库 Python 中实现了一个最小的持久执行引擎。它支持：

- 将输入和输出记录到 JSON 事件日志的 `@activity` 装饰器。
- 对活动进行排序的工作流函数。
- 重放已完成活动而不重新执行的 `run_or_replay(workflow, event_log)` 函数。

驱动程序模拟一个三活动工作流，中途崩溃，并显示（a）朴素重试重新执行所有内容与（b）重放只运行缺失活动。

## 交付它

`outputs/skill-durable-execution-review.md` 审查提议的长时运行智能体部署的正确持久执行形状：活动、确定性、检查点后端、人类输入状态和恢复时 HITL 策略。

## 练习

1. 运行 `code/main.py`。观察朴素重试和重放之间活动执行计数的差异。更改崩溃点并显示重放计数相应变化。

2. 将玩具引擎转换为明确使用 `thread_id`。模拟两个并发会话共享引擎，并确认它们的事件日志不冲突。

3. 在玩具引擎中取一个活动。引入非确定性（工作流决策中的挂钟时间戳）。演示重放时的发散。解释真实引擎如何处理这个（副作用注册、`Workflow.now()` API）。

4. 阅读 LangChain 的"生产深度智能体背后的运行时"文章。列出运行时持久化的每个状态，并命名每个状态覆盖的失败模式。

5. 为 6 小时自主编码任务设计检查点策略。你在哪里检查点？崩溃恢复是什么样的？什么需要新鲜的 HITL？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Workflow（工作流） | "智能体的脚本" | 确定性编排代码；可从事件日志重放 |
| Activity（活动） | "一个步骤" | 非确定性单元（LLM 调用、工具调用）；之前和之后记录 |
| Event log（事件日志） | "后备存储" | 每个状态转换的持久记录 |
| Replay（重放） | "恢复" | 重新运行工作流；已完成活动返回记录的结果而不重新执行 |
| Checkpoint（检查点） | "存档点" | 由 thread_id 键控的持久状态；恢复时最新获胜 |
| thread_id | "会话键" | 范围界定持久状态的标识符 |
| 35-minute degradation（35 分钟退化） | "可靠性衰减" | METR：成功率随时域大致二次方下降 |
| Non-determinism（非确定性） | "重放时的漂移" | 挂钟、随机、LLM 输出；必须注册为副作用 |
