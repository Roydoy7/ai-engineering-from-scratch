# 生产级扩展——队列、检查点与持久性（Production Scaling — Queues, Checkpoints, Durability）

> 将多智能体系统扩展到数千个并发运行需要**持久化执行**。LangGraph 的运行时在每个超步（super-step）之后以 `thread_id` 为键写入检查点（默认使用 Postgres）；工作者崩溃时释放租约，另一个工作者恢复执行。智能体可以无限期地休眠等待人类输入。**MegaAgent**（arXiv:2408.09955）每个智能体维护一个生产者-消费者队列，具有三种状态（空闲/处理中/响应中），以及两层协调（组内聊天 + 组间管理员聊天）。对于 LLM 流式传输，**Fiber/async** 优于每个任务一个线程：线程 99% 的时间在等待 token 而空闲，fiber 则在 I/O 时协作性地让出控制权。反面观点：Ashpreet Bedi 的《扩展智能体软件》主张使用 **FastAPI + Postgres + 别无其他**，直到负载证明需要其他方案——简单架构往往比预期走得更远。本课构建持久化检查点日志、每智能体工作队列（带状态转换）和 async-vs-thread 演示，并落实务实的"从简单开始"规则。

**类型：** 学习 + 构建  
**语言：** Python（标准库，`asyncio`，`sqlite3`）  
**前置知识：** Phase 16 · 09（并行群体网络）、Phase 16 · 13（共享记忆）  
**预计时间：** 约 75 分钟

## 问题所在

一个原型多智能体系统在一台笔记本电脑上用三个智能体在内存事件循环中运行良好。你移到生产环境：

- 智能体有时运行数小时（长期研究、人机循环等待）。
- 工作进程会崩溃。重启会丢失状态。
- 峰值负载是平均值的 10 倍；你需要水平扩展。
- 用户按智能体运行次数付费；你需要精确一次的计费语义。

内存事件循环无法满足这些需求。你需要在其下方有一个持久化执行层。2026 年的标准选项是：

1. 带有检查点的工作流引擎（Temporal、LangGraph 运行时）。
2. 带有状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. Actor 模型框架（MegaAgent 的每智能体生产者-消费者）。
4. 手工搭建的 FastAPI + Postgres（Bedi 的论点）。

本课构建每种方案的微缩版本。

## 核心概念

### 持久化执行——这个模式

持久化执行引擎在每个"步骤"（LangGraph 语言中的超步）之后持久化完整的程序状态。崩溃时：

```
工作者在步骤中途崩溃
  -> 租约超时
  -> 另一个工作者拾取 thread_id
  -> 从最后一个检查点恢复
  -> 没有重复的副作用
```

这需要以下条件：

- **可序列化的状态。** 所有智能体状态都必须是可持久化的。带有活动数据库连接的函数闭包无法存活。
- **确定性恢复。** 给定相同的状态和相同的输入，智能体产生相同的行动（或对 LLM 调用使用外部确定性预言机）。
- **幂等的副作用。** 外部调用（工具调用、支付）必须是幂等的，或使用去重键。

LangGraph 在每个超步后写入检查点；Temporal 在每个活动后写入；Restate 使用事件溯源日志。三者都实现了相同的模式。

### LangGraph 的运行时

每个智能体都有一个 `thread_id`；状态是一个类型化字典；每个超步向检查点表写入一行。恢复时，运行时从最后一个检查点重放，而不是从头开始。智能体可以 `interrupt()` 等待人类输入；运行时会持久化并释放工作者。当输入到达时，任何工作者都可以恢复。

这是 2026 年 4 月的参考生产设计。

### MegaAgent 的每智能体队列

arXiv:2408.09955 描述了一个规模实验：在一个集群中有数千个并发智能体。架构：

```
智能体 i：
  状态 ∈ {空闲, 处理中, 响应中}
  in_queue   <- 发给智能体 i 的消息
  out_queue  -> 回复 + 副作用

协调者：
  组内聊天  （同一组的智能体）
  组间管理员聊天  （高层路由）
```

两层协调使组内对话可以密集进行，而组间通信保持稀疏——这是将数千个智能体的成本保持线性的模式。

### Async vs 每个任务一个线程

LLM 调用是 I/O 密集型的。等待下一个 token 的线程 99% 的时间都在空闲。每个线程约占用 1MB RAM；在 10,000 个并发调用时，仅堆栈就需要 10GB。

Fiber（Python `asyncio`，Go goroutine，Rust `tokio`）在 I/O 时协作性地让出控制权。同样的 10,000 个调用可以舒适地放入一个进程。在 LLM 智能体规模下，async 不是优化——而是架构本身。

例外：CPU 密集型后处理（嵌入、分词器技巧）仍然需要线程或进程。将你的 I/O 层与 CPU 层分开。

### Bedi 的反对意见

《扩展智能体软件》（Ashpreet Bedi，2026 年）认为大多数团队在测量负载之前就过度设计了。务实的默认选择：

- FastAPI + Postgres。
- 每个智能体运行是一行；状态使用乐观并发原地更新。
- 通过 `pg_notify` 或简单的 Celery 工作者处理后台任务。
- 应用代码中的重试策略。

对于管理任务上约 100 个并发智能体运行以下的负载，这通常已经足够。测量到它失败时再升级。

规则：当你遇到简单架构无法解决的具体问题时，才采用持久化执行框架。过早采用会在不产生回报的繁文缛节上浪费时间。

### 精确一次语义

对于付费的智能体运行，你需要"有效精确一次"（至少一次投递 + 幂等消费者）。工程手段：

- **每次运行的去重键。** 将其包含在每个副作用调用中。
- **发件箱模式。** 副作用先写入表，然后由单独的进程执行。两个步骤都是幂等的。
- **补偿事务。** 当副作用成功但其追踪写入失败时，安排一个补偿操作。

这些都是数据库工程模式，不是 LLM 专属的。LLM 的额外负担只是 LLM 调用很慢；其他一切都是标准的分布式系统。

### 彩虹部署

Anthropic 的多智能体研究系统使用"彩虹部署"：多个版本的智能体运行时并发运行，这样长时间运行的智能体不必在每次代码部署时被终止。在一部分流量上进行新版本的金丝雀测试；当旧版本的智能体完成后，停用旧版本。

这是长时间运行有状态系统的标准做法；2026 年的适配是智能体可以存活数小时，因此部署周期必须适应这一点。

### 标准生产检查清单

- 持久化状态（检查点、快照，或发件箱 + 可重放日志）。
- 幂等的副作用。
- LLM 调用的异步 I/O 层。
- 至少一次投递配合去重。
- 有状态工作负载的彩虹/金丝雀部署。
- 可观测性：每智能体追踪、超步审计、重试计数器。

## 构建它

`code/main.py` 实现了：

- `CheckpointStore` — 以 thread-id 为键的 SQLite 后端检查点日志。每个超步追加一行。
- `run_with_checkpoint(agent, thread_id)` — 模拟运行中途崩溃；第二个工作者从最后一个检查点恢复。
- `AgentQueue` — 带有小型工作队列的每智能体空闲/处理中/响应中状态机。
- `demo_async_vs_threads()` — 通过 asyncio 和线程分别运行 500 个并发模拟"LLM 调用"；报告挂钟时间和峰值内存（近似值）。

运行：

```
python3 code/main.py
```

预期输出：模拟崩溃后检查点恢复成功；async 版本在 < 1 秒内处理 500 个并发调用；线程版本需要数秒，每个并发单元使用的内存量级更大。

## 交付它

标准生产加固：

- **从简单开始（Bedi 规则）。** FastAPI + Postgres，直到测量到它失败。
- **在优化之前对一切进行监控。** 每次运行的延迟直方图、每步时间、重试次数、失败分类。
- **副作用使用发件箱模式。** 特别是支付和外部 API 调用。
- **彩虹部署。** 部署期间永远不要终止正在进行的智能体运行。
- **在遇到具体问题时**采用持久化执行引擎（Temporal / LangGraph / Restate）：长达数小时的人机循环等待、跨区域协调、复杂的重试/补偿策略。
- **I/O 层使用 Async。** 线程仅用于 CPU 密集型后处理。

## 练习

1. 运行 `code/main.py`。确认检查点恢复工作正常；测量 async vs 线程并发差异。
2. 实现一个**发件箱**表：每次工具调用首先写入发件箱，然后由单独的 goroutine/任务执行。通过两次运行工具调用来验证幂等性。
3. 模拟**彩虹部署**：两个并发运行时版本；将新的 thread_id 各一半路由到每个版本；确认旧版本上正在进行的线程不会被中断。
4. 阅读 LangGraph 的运行时文档（链接如下）。识别哪些运行时功能在手工搭建的 FastAPI + Postgres 版本中复制起来最耗时。这是采用它的理由，还是可以推迟？
5. 阅读 MegaAgent（arXiv:2408.09955）第 3 节。两层协调（组内 + 组间管理员聊天）是显式的。勾勒如何将其映射到具有两个队列家族的消息队列。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Durable execution（持久化执行） | "持久化程序状态" | 引擎在每个超步后写入状态；崩溃恢复是确定性的。 |
| Super-step（超步） | "事务边界" | 检查点之间的工作单元。LangGraph 术语。 |
| thread_id | "智能体运行标识符" | 绑定检查点和恢复逻辑的键。 |
| Idempotency（幂等性） | "可以安全重试" | 重复副作用产生与一次尝试相同的结果。 |
| Outbox pattern（发件箱模式） | "解耦副作用" | 将意图写入表；单独的执行者执行并标记完成。 |
| At-least-once delivery（至少一次投递） | "可能有重复" | 消息队列语义；去重键使消费者有效精确一次。 |
| Rainbow deploy（彩虹部署） | "重叠版本" | 长时间运行工作负载期间多个运行时版本并发运行。 |
| Async fiber（异步 fiber） | "协作让出" | 用户态并发；对于 I/O 密集型负载比线程廉价得多。 |
| Checkpoint（检查点） | "状态快照" | 超步边界的序列化状态；恢复的关键。 |
