# 角色专业化——规划者、批评者、执行者、验证者（Role Specialization — Planner, Critic, Executor, Verifier）

> 2026 年最常见的多智能体分解方式：一个智能体规划，一个执行，一个批评或验证。MetaGPT（arXiv:2308.00352）将其形式化为编码进角色提示词的 SOP——产品经理、架构师、项目经理、工程师、QA 工程师——遵循 `Code = SOP(Team)` 的公式。ChatDev（arXiv:2307.07924）通过"聊天链"将设计师、程序员、审查者、测试者串联起来，并引入"交流式去幻觉"（智能体在继续之前明确请求缺失的细节）。验证者是承重角色：Cemri 等人（MAST，arXiv:2503.13657）证明每一次多智能体失败都可以追溯到缺失或损坏的验证环节。PwC 报告指出，在 CrewAI 中加入结构化验证循环后，准确率从 10% 提升到 70%，足足 7 倍的提升。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**前置知识：** Phase 16 · 04（原语模型）、Phase 16 · 05（监督者模式）  
**预计时间：** 约 60 分钟

## 问题所在

通用型多智能体系统产出通用型结果。三个程序员在群聊中一起写出三种风格的平庸代码。你可以增加更多智能体，增加更多轮次，却依然跨不过质量门槛。

解决方案不是更多智能体——而是*不同*的智能体。分配明确的角色。给批评者配置规划者没有的工具。给验证者一套客观测试集。这样，系统内部就会产生基于有据可查的纠正而非简单的并行猜测。

## 核心概念

### 四个规范角色

**规划者（Planner）。** 读取目标，产出步骤清单或规范说明。工具：知识检索、文档查阅。输出：结构化计划。

**执行者（Executor）。** 逐步读取计划，生成产物。工具：实际工作工具（代码编译器、Shell、API 客户端）。输出：产物本身。

**批评者（Critic）。** 对照规划者的意图审查执行者的输出。工具：只读访问产物、静态分析。输出：接受/拒绝，附带理由。

**验证者（Verifier）。** 读取产物并运行确定性检查。工具：测试运行器、类型检查器、Schema 验证器。输出：通过/失败，附带证据。

批评者是主观的、有立场的，通常基于 LLM。验证者是客观的、确定性的，通常基于代码。两者是不同的角色。

### MetaGPT 的 SOP 模式

MetaGPT（arXiv:2308.00352）将软件工程 SOP 编码为角色提示词：

- **产品经理**撰写 PRD（产品需求文档）。
- **架构师**生成系统设计。
- **项目经理**拆分任务。
- **工程师**实现代码。
- **QA 工程师**执行测试。

每个角色都有严格的输入/输出 Schema。角色提示词明确说明该角色*是什么*以及它*必须产出什么*。`Code = SOP(Team)` 的公式——确定性的 SOP 将一支 LLM 团队转化为可预测的流水线。

### ChatDev 的交流式去幻觉

ChatDev 增加了一个关键动作：当执行者需要计划中未包含的具体细节时，在继续之前先向设计师明确提问。这防止了 LLM 最经典的失败——貌似合理地凭空捏造细节。

实现方式：角色提示词包含这样的指令："当你需要未被给出的具体信息时，在产出任何内容之前先向相关角色点名提问。"

### 为什么验证者是最重要的角色

Cemri 等人（MAST）追踪了 1642 次多智能体执行失败。21.3% 属于验证缺口——系统交付了一个没有人检查过的答案。其余 79% 通常也能追溯到"存在一个检查步骤，但它静默地失败了，或根本从未运行"。验证是承重角色。

PwC 报告（CrewAI 部署，2025 年）：加入结构化验证循环后，准确率从 10% 提升到 70%。一个角色带来了 7 倍的提升。

### 批评者与验证者的区别

- 批评者是 LLM 对产物进行质量审查。主观的，有立场的，容易被措辞合理的内容欺骗。
- 验证者是在产物上运行的确定性程序。客观的，给出通过/失败及证据，无法被欺骗。

两者都要用。批评者捕捉验证者无法表达的品味问题。验证者捕捉批评者看不到的 bug——因为那些 bug 只在运行时才会暴露。

### 反模式

系统中每个角色都是 LLM，每个角色的输出都是"看起来不错"。这是经典的 MAST 失败模式。至少要加入一个验证者，其通过/失败由代码决定，而非由 LLM 决定。

### 框架映射

- **CrewAI** — `Agent(role, goal, backstory)` 是专业化最直观的接口。
- **LangGraph** — 节点可以有专业化的提示词；边来强制执行流水线。
- **AutoGen** — 在 GroupChat 中使用带有特定名称的角色专用 ConversableAgent。
- **OpenAI Agents SDK** — 角色专用 Agent 之间通过交接工具传递控制权。

## 构建它

`code/main.py` 实现了一个构建简单 Python 函数的 4 角色流水线：

- **规划者**生成规范说明。
- **执行者**生成代码字符串。
- **批评者**（LLM 模拟）标出明显问题。
- **验证者**在沙箱中运行生成的代码（`exec`），对照测试用例进行检验。

演示运行两次：一次执行者产出正确代码（批评者 + 验证者均通过），一次执行者产出不符合规范的代码（批评者因代码看起来合理而放过了 bug，验证者因测试失败而捕获了它）。

运行：

```
python3 code/main.py
```

## 使用它

`outputs/skill-role-designer.md` 接受一个任务，产出角色花名册（3-5 个角色）、每个角色的输入/输出 Schema，以及验证者检查内容。在将智能体接入框架之前，先运行这个技能。

## 交付它

检查清单：

- **至少一个确定性验证者。** 永远不要全部使用 LLM。
- **每个角色都有明确的输入/输出 Schema。** 规划者返回规范说明，而非散文；执行者读取该 Schema。
- **交流式去幻觉。** 执行者在信息缺失时必须向规划者提问；绝不自行捏造。
- **批评者/验证者的顺序。** 先运行批评者（廉价，捕获设计问题），再运行验证者（耗时，捕获 bug）。
- **循环预算。** 批评者-执行者修订循环最多 2 轮，超过后提交人工处理。

## 练习

1. 运行 `code/main.py`，观察验证者如何捕获批评者放过的 bug。添加一个静态分析检查（统计 `return` 出现的次数）作为额外的验证器。它能捕获什么是运行时测试遗漏的？
2. 添加第 5 个角色："需求分析师"，将用户愿望转化为规划者可用的规范说明。什么样的交流式去幻觉请求应当向上传给它？
3. 阅读 MetaGPT 第 3 节（"Agents"）。列出 MetaGPT 5 个角色各自的输入/输出 Schema。
4. 阅读 ChatDev 的聊天链图示（arXiv:2307.07924 图 3）。识别交流式去幻觉在哪里打破了一个否则会无限循环的循环。
5. PwC 的 7 倍准确率提升来自验证循环。假设三个场景，在这些场景中添加验证者不会有帮助——即确定性地检查正确性是不可能的或成本极高的。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Role specialization（角色专业化） | "不同的智能体，不同的工作" | 为规划者/执行者/批评者/验证者角色专门调校的不同系统提示词。 |
| SOP pattern（SOP 模式） | "编码的标准作业程序" | MetaGPT 的框架：每个角色严格的输入/输出 Schema 将一支团队转化为流水线。 |
| Communicative dehallucination（交流式去幻觉） | "问了再动笔" | ChatDev 模式：执行者在细节缺失时询问规划者，而不是自行捏造。 |
| Critic（批评者） | "LLM 审查者" | 主观的、有立场的审查者。捕获品味问题。可能被措辞合理的内容欺骗。 |
| Verifier（验证者） | "确定性检查" | 基于代码的通过/失败。测试运行器、类型检查器、Schema 验证器。无法被欺骗。 |
| Verification gap（验证缺口） | "没有人检查" | MAST 失败的 21.3%。答案在未经任何本可发现 bug 的检查的情况下被交付。 |
| Revision loop（修订循环） | "批评者打回重做" | 批评者拒绝触发执行者带着反馈重新运行。需要设置预算上限。 |
| All-LLM anti-pattern（全 LLM 反模式） | "看起来不错" | 每个角色都是 LLM，没有确定性检查。经典的 MAST 失败。 |
