# 并行/群体/网络化架构（Parallel / Swarm / Networked Architectures）

> 与监督者模式形成鲜明对比：没有中央决策者。智能体读取共享事件总线，异步拾取工作，将结果写回。LangGraph 明确支持针对去中心化、动态环境的"群体架构"。Matrix（arXiv:2511.21686）将控制流和数据流都表示为通过分布式队列传递的序列化消息，以消除编排者瓶颈。权衡是明确的：以确定性和可追溯性换取可扩展性。群体适用于有大量独立子问题的任务；它不适用于需要单一连贯计划的任务。

**类型：** 学习 + 构建  
**语言：** Python（标准库，`threading`，`queue`）  
**前置知识：** Phase 16 · 05（监督者模式）、Phase 16 · 04（原语模型）  
**预计时间：** 约 75 分钟

## 问题所在

监督者模式可以扩展到几十个工作者。那几百个呢？监督者本身就会成为瓶颈：每一个关于"谁来做什么"的决定都要通过一个智能体。一个缓慢的规划步骤会拖停整个系统。

群体架构颠覆了这种设计。不再由中央规划者派发工作，而是由工作者自行从共享队列中拾取任务。"协调"被烘焙进了事件总线的语义中。没有编排者；系统的扩展能力上限等于队列本身的上限。

## 核心概念

### 结构形态

```
                ┌──── 共享队列 ────┐
                │                  │
       ┌────────┼────────┐  ◄──────┴───┐
       ▼        ▼        ▼             │
     工作者  工作者  工作者   工作者
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            结果池
```

没有编排者。每个工作者循环执行：拉取任务、处理、写入结果（并可选地将后续任务入队）。

### 群体适用的场景

- **大量独立任务。** 抓取、转换、分类。任务之间不相互依赖。
- **执行时间不均匀的工作。** 如果某些任务耗时 100ms、另一些耗时 10s，群体会自动均衡负载——快速工作者会拉取下一个任务。监督者则必须提前预估时长。
- **吞吐量优先于确定性。** 你关心的是总完成时间，而非严格的执行顺序。

### 群体失效的场景

- **有序工作流。** 如果步骤 3 需要步骤 2 的输出，群体会有步骤 3 在步骤 2 完成前就触发的风险。
- **需要全局规划的任务。** 复杂研究问题需要规划者。一群研究型智能体产出的是独立事实，而非连贯报告。
- **调试。** 没有中央日志且工作异步进行，复现一个 bug 的代价很高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年将群体思路推向其自然终点的论文：控制流和数据流都是分布式队列上的序列化消息。没有中央协调者。容错能力来自消息的持久性。可扩展性是消息代理的问题，而不是系统的问题。

核心贡献：一种编程模型，其中多智能体协调的问题变成了"这个智能体订阅哪个消息主题？"而非"监督者下一个选择哪个智能体？"这使得系统看起来像一个发布/订阅事件网格。

### LangGraph 的群体架构

LangGraph 2025 年文档明确将"群体架构"描述为多智能体模式之一：智能体是节点，但边形成一个带有循环的有向图，任何节点都可以从池中被激活。工作者按条件从可用工作中拾取，而非由监督者指派。

### 失效模式：饥饿与热点

如果所有工作者都拾取最快完成的任务，耗时长的任务就永远不会被选中，直到只剩它们为止。这就是经典的队列饥饿问题。

缓解措施：
- 带有显式老化机制的优先级队列（等待时间越长，优先级越高）。
- 工作者专业化：某些工作者只处理"耗时长"的任务。
- 背压：限制快速任务进入队列的数量。

### 与基于内容路由的关联

群体与基于内容的路由（第 22 课）天然契合。不用通用队列，而是每种消息类型一个队列。专业化工作者只订阅自己的类型。这是可扩展到数千个智能体的消息总线架构的基础。

## 构建它

`code/main.py` 实现了一个由 4 个工作者线程组成的群体，它们从共享的 `queue.Queue` 中拉取任务。任务具有可变的执行时长（有些很快，有些很慢）。演示对比了：

- **顺序基线：** 单个工作者串行处理所有任务。
- **固定分配：** 每个任务预先分配给特定工作者（监督者风格）。
- **群体：** 工作者从共享队列中拉取。

群体自动均衡负载；固定分配则在某个工作者的指定任务耗时很长时，让其他快速工作者白白空闲。

运行：

```
python3 code/main.py
```

输出显示每个工作者处理的任务数量（群体分配不均但最优）和挂钟时间。

## 使用它

`outputs/skill-swarm-fit.md` 评估某个任务是否应使用群体还是监督者模式。输入：任务独立性、时长方差、排序要求、调试可行性需求。

## 交付它

检查清单：

- **带老化机制的优先级队列。** 防止长任务饥饿。
- **工作者幂等性。** 如果工作者在执行过程中崩溃，任务可能被拉取多次。工作者必须是幂等的。
- **持久化队列。** 在生产中使用 Kafka、Redis Streams 或数据库支持的队列。`queue.Queue` 只是内存队列。
- **每个任务的可观测性。** 每个任务都有追踪 ID；每个工作者用追踪 ID 记录开始/结束时间。
- **背压。** 如果队列增长速度快于工作者消耗速度，降低生产者的速率。

## 练习

1. 运行 `code/main.py`。在可变时长工作负载上，群体比顺序执行快多少？比固定分配快多少？
2. 添加优先级队列变体（使用 `queue.PriorityQueue`）。按任务的"重要性"字段分配优先级。观察在持续负载下低优先级任务是否会发生饥饿。
3. 实现热点检测器：当某个工作者处理的任务数量达到最慢工作者的 3 倍时记录警告。这说明任务时长分布的什么问题？
4. 阅读 Matrix 论文（arXiv:2511.21686）摘要和第 3 节。识别 Matrix 接受的一个具体权衡（可扩展性收益）和它放弃的一个（可追溯性、确定性）。
5. 将群体演示改造为使用包含 `(task_type, payload)` 元组的 `queue.Queue`，工作者只订阅特定类型。当任务是异质的时，什么样的路由规则最合理？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Swarm architecture（群体架构） | "去中心化智能体" | 工作者从共享队列中拉取；没有中央编排者。 |
| Event bus（事件总线） | "智能体订阅主题" | 按类型或内容将任务路由到工作者的消息代理。 |
| Starvation（饥饿） | "任务永远不运行" | 低优先级任务因高优先级工作持续涌入而永远不被选中。 |
| Hot-spotting（热点） | "某个工作者被淹没" | 负载不均衡，某个工作者承担了大部分任务。 |
| Back-pressure（背压） | "降低生产者速率" | 当队列填满时向上游发出信号以停止生产的机制。 |
| Idempotent worker（幂等工作者） | "可以安全重复执行" | 同一个任务被处理两次会产生相同结果。这是工作者崩溃后的必要保证。 |
| Durable queue（持久化队列） | "崩溃后仍存在" | 由磁盘或复制存储支持的队列；工作者崩溃时任务不会丢失。 |
| Matrix framework（Matrix 框架） | "完整消息传递群体" | 数据流和控制流都是分布式队列上的序列化消息。 |
