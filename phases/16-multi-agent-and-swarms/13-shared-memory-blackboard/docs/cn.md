# 共享记忆与黑板模式（Shared Memory and Blackboard Patterns）

> 2026 年的多智能体系统中并存着两种方式：**消息池**（每个人看到每个人的消息，如 AutoGen GroupChat 或 MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如 Context-Aware MCP 或 Matrix 框架）。两者都是多智能体系统中唯一有状态的部分——这意味着有趣的 bug 都藏在这里。参考性的失效模式是**记忆中毒**：一个智能体幻觉出一个"事实"，其他智能体将其视为已验证的信息，准确性逐渐衰减，比立即崩溃要难调试得多。本课用标准库构建这两种结构，注入一次中毒攻击，并展示在生产中真正有效的三种缓解措施。

**类型：** 学习 + 构建  
**语言：** Python（标准库，`threading`）  
**前置知识：** Phase 16 · 04（原语模型）、Phase 16 · 09（并行群体网络）  
**预计时间：** 约 75 分钟

## 问题所在

多智能体系统需要一个地方让智能体共享事实。一种字面意义上的选择是"把一切都放在消息里传递"——但这只是用额外的复制重新发明了共享状态。另一种是"给所有人一个全局日志"——但全局日志会无限增长，且很容易被污染。第三种是"为每个智能体投影一个视图"——可扩展，但需要大量 Schema 设计。

当某个智能体产生幻觉并将其写入共享状态时，每个读取该状态的下游智能体都会将这个幻觉当作事实接受。等到人类注意到时，推理链已经深入五步，而根本原因却是第三条曾经写下的消息。调试多智能体准确性衰减比调试崩溃难得多。

这就是记忆中毒。它是 MAST 分类体系（Cemri 等人，arXiv:2503.13657）中记录最多的第二大失效家族，而且它是结构性的：任何没有来源追溯和不可写验证者的共享记忆设计最终都会遭遇它。

## 核心概念

### 两种主要拓扑

**完整消息池。** 每个智能体读取每条消息。AutoGen GroupChat 和 MetaGPT 使用这种方式。简单、透明、可检查，但超过约 10 个智能体后就无法扩展，因为每个智能体的上下文都会充满其他智能体的工作内容。

```
智能体A ──写入──▶ ┌────────────────┐ ◀──读取── 智能体D
                  │   消息池       │
智能体B ──写入──▶ │                │ ◀──读取── 智能体E
                  │  （全局日志）  │
智能体C ──写入──▶ └────────────────┘ ◀──读取── 智能体F
```

**带订阅的黑板。** 智能体声明对主题的兴趣；底层基础设施只路由相关消息。CA-MCP（arXiv:2601.11595）和 Matrix 去中心化框架（arXiv:2511.21686）使用这种方式。可扩展性更强，但需要预先设计 Schema 以使订阅有意义。

```
                  ┌─ 主题：价格 ──┐
智能体A ──发布──▶ │               │ ──▶ 智能体D（已订阅）
                  ├─ 主题：订单 ──┤
智能体B ──发布──▶ │               │ ──▶ 智能体E（已订阅）
                  ├─ 主题：警报 ──┤
智能体C ──发布──▶ │               │ ──▶ 智能体F（已订阅）
                  └───────────────┘
```

### 各自的优势场景

- **完整消息池**适用于智能体数量少（< 10）、角色多样、且对话周期短的情况。当所有人都能看到一切时，弄清楚谁说了什么很容易。
- **黑板**适用于智能体数量多、角色同质但实例众多（群体），以及对话长期运行的情况。路由节省了 token 成本和上下文污染。

生产系统通常混合使用：顶层（规划层）使用小型完整池，底层（工作者层）使用黑板。

### 记忆中毒：一个具体场景

三个智能体在研究任务上协作。智能体 A 是检索智能体，智能体 B 是摘要智能体，智能体 C 是分析智能体。

1. A 获取一个页面并向共享状态写入消息："研究报告显示准确率提升了 42%。"
2. 实际上被获取的页面写的是"提升了 4.2%"。A 产生了一个小数点幻觉。
3. B 读取共享状态后写道："报告了大幅 42% 的准确率提升（来源：A）。"
4. C 读取共享状态后写道："建议采用——42% 的提升具有变革性意义。"
5. 最终报告引用了一个从未存在过的 42% 的数字。

没有任何智能体崩溃。没有测试失败。系统"正常运行"了。幻觉通过共享状态从一个智能体的上下文传播到了所有下游智能体的推理中。

### 为什么这是结构性问题

没有共享状态时，智能体 A 的幻觉停留在 A 的上下文中。下游智能体会重新获取或重新推导，可能会发现错误。有了朴素的共享状态，A 的上下文变成了所有人的上下文，幻觉被洗白为事实。

问题不在于共享状态本身——而在于**没有来源追溯、没有独立验证者**的共享状态。三种缓解措施解决了这个问题：

1. **在每次写入时标注来源。** 共享状态中的每条记录都记录了谁写的、何时写的、在什么提示词下写的，以及（如果适用）智能体引用了什么来源。下游智能体基于来源信息带着合理怀疑来读取。
2. **版本化写入；将其视为只可追加。** 纠正是一条新记录，它取代旧记录，而不是原地更新。审计追踪得以保留。
3. **保留至少一个无法向共享状态写入的智能体。** 一个只读的验证者智能体对记录进行采样，重新获取被引用的来源，并标记不一致之处。由于它不能向池写入，它就不会被池中毒。

### 黑板的历史先例（Hayes-Roth，1985 年）

黑板模式比 LLM 智能体早了四十年。Hayes-Roth（1985 年，《控制的黑板架构》）描述了观察全局黑板、贡献部分解决方案并触发其他知识源的专业知识源。2026 年的黑板（CA-MCP、Matrix）是同一个模式，只是将 LLM 智能体作为知识源，将 JSON 数据块作为部分解决方案。旧文献中记录了关于写入争用、机会性控制和一致性的解决方案，这些正是现代系统在重新发现的东西。

### 投影 vs 完整视图

纯黑板给每个订阅者相同的投影（主题范围）。更积极的设计是**每智能体投影**：每个智能体获得为其角色定制的视图。LangGraph 的状态归约器是 2026 年的规范实现——归约函数将全局状态折叠成角色特定的切片。

每智能体投影的可扩展性更强，但需要 Schema。没有 Schema，你就得在每个智能体的提示词中重新构建即兴的投影。

### 写入争用模式

多个智能体同时写入是一个并发问题，而不仅仅是 LLM 问题。三种模式有效：

- **顺序写入者（单一生产者）。** 所有写入通过一个协调智能体串行化。简单，但会成为瓶颈。
- **带版本控制的乐观并发。** 每条记录都有版本号；写入者在版本不匹配时失败并重试。经典的数据库技术。
- **主题分区。** 不同智能体拥有不同的主题。没有跨主题争用。需要预先设计分区边界。

大多数 2026 年的框架默认使用顺序写入者，因为 LLM 调用速度够慢，争用很少见，瓶颈不会造成困扰。

### 不可写的验证者

最有分量的缓解措施是只读验证者。实现规则：

- 验证者与团队共享状态（读取黑板或池）。
- 验证者没有共享状态的写入句柄——只能写入单独的验证渠道。
- 验证者独立获取写入中引用的来源。标记分歧。
- 验证者的输出路由到人类或单独的决策智能体，永远不会被反馈回池中。

没有这种分离，验证者的输出就会成为池中的新记录，这意味着被中毒的池会毒化验证者，进而毒化它的验证结果。

## 构建它

`code/main.py` 在 stdlib Python 中实现了两种拓扑，加上一个玩具级中毒攻击和三种缓解措施。

- `MessagePool` — 线程安全的只可追加日志，支持完整读取。
- `Blackboard` — 按主题键控的发布/订阅，支持每智能体订阅。
- `ProvenanceEntry` — 每次写入记录（写入者、时间戳、提示词哈希、来源 URI）。
- `PoisoningScenario` — 运行一个三智能体研究任务，其中智能体 A 对一个小数点产生幻觉。打印最终报告。
- `Verifier` — 一个只读智能体，重新获取来源并标记不一致。运行带有验证者的同一场景。

运行：

```
python3 code/main.py
```

预期输出：
- 第 1 次运行（无验证者）：幻觉出的 42% 传播到最终报告。
- 第 2 次运行（带验证者）：验证者标记不一致，池被标记为"已标记"，最终报告包含撤回说明。

## 使用它

`outputs/skill-memory-auditor.md` 是一个技能，用于审计任何多智能体系统的共享记忆设计，检查来源追溯、版本控制和验证者分离。在投入生产之前，对新的多智能体架构运行此技能。

## 交付它

对于任何共享记忆设计：

- 在每次写入时记录来源：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 使日志只可追加。纠正是新记录，引用被取代的旧记录。
- 至少部署一个拥有独立来源访问权限的只读验证者智能体。
- 将验证者输出路由到单独的渠道，而非反馈回共享池。
- 记录被取代的写入比例——比例上升是幻觉模式的早期证据。

## 练习

1. 运行 `code/main.py`。确认第 1 次运行传播了幻觉，第 2 次运行捕获了它。
2. 添加第二个幻觉：智能体 B 虚构了一个数据集大小。验证者应该在不针对任何一个进行特殊调优的情况下捕获两个。
3. 将完整池切换为带主题分区（`prices`、`summaries`、`analyses`）的黑板。主题分区让哪些中毒场景更难以实施，哪些又没有帮助？
4. 阅读 Hayes-Roth（1985 年，《控制的黑板架构》）。识别论文中提到的、但本课未讨论的两种控制模式，这些模式对 2026 年的系统仍有价值。
5. 阅读 CA-MCP（arXiv:2601.11595）。将其共享上下文存储映射到 `code/main.py` 中的 `MessagePool` 或 `Blackboard` 类。CA-MCP 在顶部增加了哪些原语？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Message pool（消息池） | "共享聊天历史" | 每个智能体都读取的只可追加日志。完全透明，但扩展性差。 |
| Blackboard（黑板） | "共享工作区" | 按主题键控的发布/订阅。智能体订阅相关主题。可扩展性更强。 |
| Provenance（来源追溯） | "谁写了什么" | 每次写入的元数据：写入者、时间戳、提示词、来源。 |
| Memory poisoning（记忆中毒） | "幻觉扩散" | 一个智能体的错误进入共享状态，下游智能体将其视为事实接受。 |
| Append-only（只可追加） | "不允许原地更新" | 纠正是取代旧记录的新记录。保留审计追踪。 |
| Unwritable verifier（不可写的验证者） | "独立审计者" | 重新获取来源并标记不一致的只读智能体。 |
| Projection（投影） | "范围化视图" | 从全局状态计算出的每智能体视图。LangGraph 归约器是典型案例。 |
| Knowledge Source（知识源） | "专家智能体" | Hayes-Roth 1985 年对黑板参与者的称谓。 |
