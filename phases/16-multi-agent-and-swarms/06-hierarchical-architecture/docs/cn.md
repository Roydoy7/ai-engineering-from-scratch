# 层级架构及其失效模式（Hierarchical Architecture and Its Failure Mode）

> 层级架构就是嵌套的监督者。管理者智能体之上是子管理者，子管理者之下是工作者。CrewAI 的 `Process.hierarchical` 是教科书式的实现：一个 `manager_llm` 动态分配任务并验证产出。LangGraph 的等价实现是 `create_supervisor(create_supervisor(...))`。当任务本身就是一张真实的组织架构图时，这种模式是最自然的选择。但它也是最容易陷入"管理者循环"的模式——管理者智能体分配工作不当、误解子产出，或无法达成共识。顺序模式往往比它更胜一筹。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**前置知识：** Phase 16 · 05（监督者模式）  
**预计时间：** 约 60 分钟

## 问题所在

一旦掌握了监督者模式，自然会产生这样的想法："如果工作者本身也是监督者呢？"团队下有子团队，公司里有部门套部门。层级架构正是对这种现实的映射。

问题在于：LLM 管理者和人类管理者不是一回事。人类管理者对下属的知识边界有稳定的先验认知。LLM 管理者每一轮都要从上下文中重新推断整个组织结构。上下文稍有偏移，整棵树就会分错工作。

## 核心概念

### 结构形态

```
                 管理者
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       子管理者 A         子管理者 B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点负责规划、委派和综合。只有叶节点真正执行工作。

### 适用场景

- **清晰的组织映射。** 如果实际任务本身就是部门化的（"法务审查文档、财务审查文档、工程审查文档，然后为高管总结"），层级关系是显式的。
- **局部摘要。** 每个子管理者在顶层管理者看到结果之前，先对本团队的产出进行综合。顶层管理者看到的是三份子管理者摘要，而不是十五份工作者原始输出。

### 失效场景

2026 年的事后分析报告一再发现三种失效模式：

1. **任务分配错误。** 管理者读取目标，凭空幻觉出一种分解方式，然后把任务委派给了错误的子管理者。由于子管理者会忠实地执行分配给它的工作，这个错误只在顶层综合时才浮出水面——已经比人类本可以发现它的位置晚了一层。
2. **产出误读。** 子管理者返回"无法验证断言 X"，顶层管理者却将其总结为"断言 X 未经确认"。每一层都在发生语义漂移。
3. **共识循环。** 两个子管理者意见相左；顶层管理者要求它们协调；它们再次向下委派；工作者重新执行；子管理者返回略微不同的答案；循环继续。CrewAI 的 `Process.hierarchical` 通过步数限制加以防护，但这个限制本身又成了一个需要调节的超参数。

### 关键判断问题

顺序（线性流水线）vs 层级：你的任务真的存在独立的子团队，还是一个线性流程被包装成了树的样子？如果是后者，使用顺序。如果是前者，使用层级，但要预留明确的协调规则和预算。

### CrewAI 的实现

`Process.hierarchical` 在专业化团队之上接入一个管理者 LLM。管理者负责：

- 接收顶层任务，
- 向各团队分配子任务，
- 评估团队产出，
- 决定是接受、重新委派，还是迭代。

文档参见：https://docs.crewai.com/en/introduction（在 Core Concepts 下查找"Hierarchical Process"）。

### LangGraph 的实现

LangGraph 使用嵌套的 `create_supervisor` 调用。内层监督者有自己的图；外层监督者将内层图视为一个不透明的节点。这对于调试来说比 CrewAI 更清晰（可以分别单步执行每个图），但对树结构的动态重塑更难表达。

参考：https://reference.langchain.com/python/langgraph-supervisor。

## 构建它

`code/main.py` 运行一个三层层级：

- 顶层管理者：将任务拆分为"工程"和"法务"两条分支，
- 工程子管理者：拆分为"前端"和"后端"工作者，
- 法务子管理者：一名工作者。

演示对比了两条路径：正常路径（各方达成一致）和**扰动路径**（顶层管理者的分解将"法务"误标为"财务"，然后观察错误如何级联——子管理者忠实地执行财务工作，顶层综合者汇报财务发现，而原始的法务问题始终悬而未决）。

运行：

```
python3 code/main.py
```

输出会并排展示两条路径，清晰对比"被问了什么"与"实际交付了什么"。

## 使用它

`outputs/skill-hierarchy-fitness.md` 评估给定任务是否应使用层级、顺序或扁平监督者模式。输入：任务描述、组织结构、协调预算。输出：模式推荐，以及需要防范的具体失效模式。

## 交付它

如果你要部署层级架构：

- **将树深限制在 2 层。** 三层已经让大多数错误超出了可观测性的范围。
- **明确的协调预算。** 在顶层管理者必须提交结果之前，设置最大轮数。通常是 2 轮。
- **每次综合都标注来源。** 每个节点的摘要必须注明是由哪些叶节点的产出生成的。
- **对分解漂移发出警报。** 记录管理者每一步的分解结果，与用户查询进行差异比对。如果分解不再覆盖原始查询，触发警报。

## 练习

1. 运行 `code/main.py`，对比正常路径与扰动路径。需要经过多少层管理者交接，顶层输出才会与用户问题完全背离？
2. 添加第三层（顶层→子层→子子层→工作者）。测量随着深度增加，扰动路径自我纠正的频率与完全背离的频率各是多少。
3. 在每个子管理者处实现一个"金丝雀"工作者，它总是接收原始用户问题且不做任何修改。用金丝雀的答案来检测分解漂移。当金丝雀的答案与综合答案不一致时，管理者应如何响应？
4. 阅读 CrewAI 的 `Process.hierarchical` 文档。识别 CrewAI 应用的一个具体防护措施（步数限制、manager_llm 约束），并描述它针对的是哪种失效模式。
5. 对比嵌套 LangGraph 监督者与 CrewAI 层级模式。哪种方式让协调循环更容易被检测到？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Hierarchical（层级） | "组织架构图模式" | 监督者之上套监督者；只有叶节点真正执行工作。 |
| Manager LLM（管理者 LLM） | "老板" | 在内部节点进行分解、分配和验证的 LLM。 |
| Decomposition drift（分解漂移） | "老板迷失了方向" | 顶层管理者的分解不再覆盖原始问题。 |
| Reconciliation loop（协调循环） | "无休止的开会" | 子管理者意见相左；顶层重新委派；工作者重新执行；循环直到预算耗尽。 |
| Depth-2 ceiling（二层深度上限） | "不要超过两层" | 经验性防护规则：三层以上会导致可观测性崩溃。 |
| Canary question（金丝雀问题） | "每层的基准真相" | 总是接收原始查询不做修改的工作者，用于检测漂移。 |
| Provenance chain（来源链） | "谁说了什么" | 从每次综合追溯到产生它的叶节点输出。 |
