# 多智能体原语模型（The Multi-Agent Primitive Model）

> 2026 年发布的每个多智能体框架——AutoGen、LangGraph、CrewAI、OpenAI Agents SDK、Microsoft Agent Framework——都是四维设计空间中的一个点。四个原语，仅此而已：智能体、交接、共享状态、编排者。本课从零开始构建它们，在所有四个上运行一个玩具系统，然后将每个主要框架映射到相同的轴上，这样你就可以用一段话读懂任何新版本。

**类型：** 学习  
**语言：** Python（标准库）  
**前置知识：** Phase 14（智能体工程）、Phase 16 · 01（为什么需要多智能体）  
**预计时间：** 约 60 分钟

## 问题所在

每六个月就有一个新的多智能体框架发布。2023 年的 AutoGen。2024 年的 CrewAI。2024 年的 LangGraph 和 OpenAI Swarm。2025 年 4 月的 Google ADK。2026 年 2 月的 Microsoft Agent Framework RC。每份新闻稿都声称自己是"正确的抽象"。

如果你试图一个接一个地学习它们，你会精疲力竭。API 看起来不同。文档对"智能体"是什么意见不一。一个框架称其共享内存为"黑板"，另一个称之为"消息池"，第三个称之为"StateGraph"。你开始怀疑这个领域只是在不断翻腾。

并非如此。在营销之下，四个原语是稳定的。学一次，一段话读懂每个新框架。

## 核心概念

### 四个原语

1. **智能体（Agent）**——系统提示加工具列表。无状态；每次运行从其系统提示和当前消息历史开始。
2. **交接（Handoff）**——从一个智能体向另一个智能体结构化的控制转移。机制上，是一个返回新智能体的工具调用，或遵循条件的图边。
3. **共享状态（Shared state）**——任何超过一个智能体可以读取（有时写入）的数据结构。消息池、黑板、键值存储、向量记忆。
4. **编排者（Orchestrator）**——决定谁接下来发言的实体。选项：显式图（确定性）、LLM 发言者选择器（软性）、上一位发言者的交接调用（OpenAI Swarm），或队列上的调度器（群体架构）。

这就是整个设计空间。每个框架为每个轴选择默认值；其余的是表面语法。

### 所有 2026 年框架如何映射到它

| 框架 | 智能体 | 交接 | 共享状态 | 编排者 |
|-----|------|------|---------|-------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | 工具返回智能体 | 调用者的问题 | LLM 的下一次交接调用 |
| AutoGen v0.4 / AG2 | `ConversableAgent` | GroupChat 上的发言者选择器 | 消息池 | 选择器函数（LLM 或轮询） |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | 任务输出链 | 管理者 LLM 或静态顺序 |
| LangGraph | 节点函数 | 图边 + 条件 | `StateGraph` 归约器 | 图，确定性 |
| Microsoft Agent Framework | 智能体 + 编排模式 | 特定于模式 | 线程/上下文 | 特定于模式 |
| Google ADK | 智能体 + A2A 卡 | A2A 任务 | A2A 工件 | 宿主决定 |

表面差异看起来很大。底层：相同的四个旋钮。

### 为什么这很重要

一旦你看到原语，框架比较就变成了一个简短的清单：

- 编排者是否信任 LLM 来路由（Swarm），还是在代码中固定路由（LangGraph）？
- 共享状态是全历史（GroupChat）还是投影的（StateGraph 归约器）？
- 智能体可以修改彼此的提示（CrewAI 管理者）还是只能交接（Swarm）？

这三个问题回答了 80% 的"哪个框架适合特定问题"的问题。你停止寻找"最好的多智能体框架"，开始为你实际关心的轴进行设计。

### 无状态洞见

除了共享状态之外，每个原语都是无状态的。智能体是（提示，工具）的函数。交接是函数调用。编排者是调度器。**系统中唯一有状态的东西是共享状态。** 所有有趣的 bug 都在那里：记忆中毒（第 15 课）、消息排序、版本控制、写入争用。

隐藏共享状态的框架（Swarm）将问题推给调用者。集中化共享状态的框架（LangGraph 检查点、AutoGen 池）使其可检查，但将协调成本转移到共享状态实现上。

### 单个原语的剖析

#### 智能体

```
Agent = (system_prompt, tools, model, optional_name)
```

没有记忆。没有状态。具有相同系统提示和工具的两个智能体是可互换的。看起来像每智能体状态的一切实际上都在共享状态或交接协议中。

#### 交接

```
Handoff = (from_agent, to_agent, reason, payload)
```

三种实现方式占主导：

- **函数返回**——工具返回下一个智能体。这是 OpenAI Swarm 模式。智能体在其工具模式中携带路由。
- **图边**——LangGraph。边是声明性的。LLM 产生一个值；条件选择下一个节点。
- **发言者选择**——AutoGen GroupChat。选择器函数（有时本身就是 LLM 调用）读取池并选择接下来谁发言。

#### 共享状态

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

最少是消息列表。通常更多：结构化工件（CrewAI 任务输出）、类型化上下文（LangGraph 归约器）、外部记忆（MCP、向量数据库）。

两种拓扑：**全池**（每个智能体看到每条消息）和**投影**（智能体看到角色范围的视图）。全池简单，扩展性差。投影池扩展，但需要前期模式设计。

#### 编排者

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

四种风格：

- **静态**——图在构建时固定（LangGraph 确定性，CrewAI 顺序）。
- **LLM 选择**——LLM 读取池并选择下一位发言者（AutoGen，CrewAI 层次）。
- **交接驱动**——当前智能体通过调用交接工具决定（Swarm）。
- **队列驱动**——工作者从共享队列中拉取；没有明确的下一位发言者（群体架构）。

### 框架之间什么变化

一旦原语固定，剩余的设计决策是：

- **记忆策略**——临时的还是耐久的检查点（LangGraph 检查点器）。
- **安全边界**——谁可以批准交接（人机循环）。
- **成本核算**——每智能体 token 预算。
- **可观察性**——追踪交接，持久化状态以供重放。

所有这些都可以在原语之上实现。它们都不是新的原语。

## 构建它

`code/main.py` 在约 150 行的标准库 Python 中实现了四个原语。没有真实的 LLM——每个智能体都是脚本化策略，所以焦点保持在协调结构上。

文件导出：

- `Agent`——名称、系统提示、工具、策略函数的数据类。
- `Handoff`——返回新智能体的函数。
- `SharedState`——线程安全的消息池。
- `Orchestrator`——三个变体：`StaticOrchestrator`、`HandoffOrchestrator`、`LLMSelectorOrchestrator`（模拟）。

演示通过所有三种编排者类型运行相同的三智能体流水线（研究→写作→审查），并在最后打印消息池。你可以看到输出只在*谁选择下一个*上有所不同；智能体和共享状态在所有运行中都是相同的。

运行：

```
python3 code/main.py
```

预期输出：三次编排者运行，每种模式一次。每次打印最终消息池。如果研究员决定提前完成，交接驱动的运行会到达较少的智能体——这是 LLM 路由权衡的缩影。

## 使用它

`outputs/skill-primitive-mapper.md` 是一个读取任何多智能体代码库或框架文档并返回四原语映射的技能。在新框架发布上运行它，在深入阅读文档之前获得一段话的理解。

## 交付它

在采用新框架之前，为其编写原语映射。如果你做不到，文档就不完整或该框架正在发明第五个原语（罕见——检查你没见过的共享状态风格）。

在架构文档中固定映射。当新团队成员加入时，在 API 文档之前发送映射给他们。当框架版本变化时，对比映射而不是变更日志。

## 练习

1. 以不同的智能体策略运行 `code/main.py` 三次。观察编排者选择如何改变哪些智能体运行。
2. 实现第四种编排者类型：一个队列驱动的，其中智能体从共享状态轮询工作。可能发生什么死锁，以及如何检测它？
3. 取 LangGraph 快速入门，将其重写为四个原语。LangGraph 的哪些抽象是 1:1 映射的，哪些是便利包装器？
4. 阅读 OpenAI Swarm 食谱。识别 Swarm 使哪个原语最符合人机工程学，以及它将哪个推给调用者。
5. 在表格中找一个完全隐藏共享状态的框架。解释当智能体需要在没有重新读取历史的情况下跨交接协调时会出什么问题。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Agent（智能体） | "带工具的 LLM" | `(system_prompt, tools, model)` 三元组。无状态。 |
| Handoff（交接） | "控制转移" | 命名下一个智能体和可选有效载荷的结构化调用。三种实现：函数返回、图边、发言者选择。 |
| Shared state（共享状态） | "记忆"/"上下文" | 多智能体系统中唯一有状态的部分。消息池或黑板。 |
| Orchestrator（编排者） | "协调者" | 决定谁下一个运行的实体。静态图、LLM 选择器、交接驱动或队列驱动。 |
| Primitive（原语） | "抽象" | 每个框架参数化的四个轴之一。不是框架特性。 |
| Message pool（消息池） | "共享聊天历史" | 全历史共享状态。易于推理，扩展性差。 |
| Projected state（投影状态） | "范围视图" | 共享状态中角色特定的视图。可扩展，需要模式设计。 |
| Speaker selection（发言者选择） | "接下来谁说话" | 函数（通常是 LLM）从群体中选择下一个智能体的编排者模式。 |
