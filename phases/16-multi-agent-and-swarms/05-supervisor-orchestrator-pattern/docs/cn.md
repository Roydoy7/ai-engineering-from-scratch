# 监督者/编排者-工作者模式（Supervisor / Orchestrator-Worker Pattern）

> 一个主导智能体负责规划和委派，专业化工作者在并行上下文中执行任务并汇报结果。这正是 Anthropic Research 系统背后的模式（以 Claude Opus 4 为主导，Sonnet 4 作为子智能体），在内部研究评估中比单智能体 Opus 4 高出 +90.2%。Anthropic 的工程博文报告指出，BrowseComp 上 80% 的方差仅由 token 用量来解释——多智能体之所以取胜，主要是因为每个子智能体都能获得全新的上下文窗口。本课从原语出发构建监督者模式，并梳理 2026 年生产部署中积累的工程经验。

**类型：** 学习 + 构建  
**语言：** Python（标准库，`threading`）  
**前置知识：** Phase 16 · 04（原语模型）  
**预计时间：** 约 75 分钟

## 问题所在

研究任务是单智能体系统最典型的失败场景。你问："2023 年到 2026 年之间，多智能体系统发生了哪些变化？"单个智能体会顺序阅读五篇论文，把一半的上下文填满论文原文，然后还要同时对所有内容进行推理。读到第五篇时，第一篇早已被遗忘。更关键的是：它无法并行处理。

监督者模式解决了这个问题：一个主导智能体规划搜索方向，把每个子问题委派给工作者，最后进行综合。每个工作者针对一个具体问题获得自己的 200k token 窗口。主导智能体永远看不到原始论文——它只看到工作者的摘要。

Anthropic 的生产级 Research 系统报告，相比单个 Opus 4，内部研究评估提升了 +90.2%。同一篇博文还指出，BrowseComp 方差的 80% 仅由 *token 用量* 解释。每个子智能体获得全新上下文，这才是核心机制。

## 核心概念

### 模式结构

```
                 ┌──────────────┐
                 │   主导者     │  规划、分解、
                 │  (Opus 4)    │  综合
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ 工作者1  │  │ 工作者2  │  │ 工作者3  │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         全新         全新         全新
         上下文       上下文       上下文
```

主导者永远不直接阅读原始资料。工作者彼此看不到对方的成果，直到主导者完成综合。每条箭头都是一次携带精简产物的交接。

### 为什么它能赢

三个核心机制：

1. **每个子智能体获得全新上下文。** 负责探索"FIPA-ACL 源流"的工作者，不会携带主导者花费在规划上的 40k token。它为一个问题获得一整个 200k 窗口。
2. **通过提示词实现专业化。** 主导者的提示词是"分解与综合"，而非"研究"。每个工作者的提示词都很窄："找出 X 中发生了什么变化。"聚焦的提示词产出聚焦的结果。
3. **并行执行。** 工作者并发运行。挂钟时间大约是 `max(工作者时间) + 规划 + 综合`，而非 `sum(工作者时间)`。

### 工程经验（Anthropic 2025）

Anthropic 博文列出了若干仍在 2026 年适用的生产经验：

- **按查询复杂度调配工作量。** 简单查询：单个智能体，3-10 次工具调用。复杂查询：10 个以上智能体。这个估算应由主导者完成，而非调用方。
- **先宽后窄。** 先将问题分解为宽泛的子问题，然后视答案深度决定是否为某个子问题再派遣更多工作者。
- **彩虹部署（Rainbow deployments）。** 智能体运行周期长且有状态，传统的蓝绿部署不适用。Anthropic 采用彩虹部署：逐步发布新版本，同时让旧版本自然耗尽。
- **Token 用量占主导。** 多智能体消耗的 token 约为单智能体的 15 倍。只有当任务价值足以覆盖成本时，才值得启用。

### LangGraph 的转向

LangGraph 最初推出了 `langgraph-supervisor` 库，并提供高层的 `create_supervisor` 辅助函数。2025 年，LangChain 将推荐方式改为直接通过工具调用实现监督者模式，因为工具调用让你对"监督者能看到什么"（上下文工程）有更精细的控制。这个库仍然可用；但文档现在更推荐工具调用形式。

### 失败模式

- **主导者对规划产生幻觉。** 如果主导者生成的子问题无法真正分解原始问题，工作者就会对错误的目标展开精确研究。
- **工作者过度探索。** 没有明确的范围边界时，工作者会偏离指定的子问题，污染综合步骤。
- **综合冲突。** 两个工作者返回相互矛盾的事实。主导者要么重新询问（增加一轮），要么明确指出分歧。最糟糕的失败是无声地选择其中一方——用户永远不知道分歧的存在。

### 何时监督者模式是错误选择

- **顺序任务。** 如果步骤 2 确实需要步骤 1 的输出，并行化没有任何收益。改用流水线（CrewAI Sequential、LangGraph 线性图）。
- **简单查询。** 单智能体处理得更快更便宜。在派遣工作者之前，先让主导者执行"工作量估算"检查。
- **严格确定性。** 监督者依赖 LLM 来选择委派对象。当审计/重放比适应性更重要时，静态图是更好的选择。

## 构建它

`code/main.py` 使用 `threading` 实现了一个带有三个并行工作者的监督者。主导者将查询分解为子问题，工作者并发处理各自的子问题，然后主导者进行综合。没有真实 LLM——工作者通过脚本模拟抓取与摘要。

关键结构：

- `Lead.plan(query)` 将查询拆分为 3 个子问题。
- `Worker.run(sub_q)` 返回一份假摘要（在生产中可以是任何使用工具的智能体）。
- `Lead.run(query)` 在线程中启动工作者，等待它们完成，然后进行综合。

运行：

```
python3 code/main.py
```

输出会显示规划结果、带有起止时间戳的并行工作者追踪，以及最终综合内容。你可以直观看到挂钟时间的收益：三个各耗时 0.3 秒的工作者在约 0.35 秒内完成，而非 0.9 秒。

## 使用它

`outputs/skill-supervisor-designer.md` 接受用户查询，生成一份监督者模式设计方案：主导者系统提示、工作者角色、子问题分解规则，以及综合模板。在构建新的研究型智能体系统前，先运行这个技能。

## 交付它

部署监督者模式前的检查清单：

- **模型搭配。** 主导者使用推理层模型（Opus 级、`o3` 级）。工作者使用更快、更便宜的模型（Sonnet、`o4-mini`）。
- **工作者超时。** 任何超过中位运行时间 2 倍的工作者都应被终止；主导者要么以更窄的范围重新派遣，要么在没有该工作者结果的情况下继续推进。
- **每个工作者的 token 上限。** 设置硬性限制（例如预期综合输入量的 10 倍），防止失控的工作者耗尽预算。
- **可观测性。** 追踪主导者的规划、每个工作者的工具调用，以及综合过程。这是事后调试的基础。
- **彩虹发布。** 有状态的长运行智能体需要逐步版本过渡，而非热切换。

## 练习

1. 运行 `code/main.py`，然后修改主导者以派遣 5 个工作者而非 3 个。观察挂钟时间的变化。在这个演示中，工作者数量增加到多少时，派遣开销会超过并行收益？
2. 实现工作者超时机制：终止任何运行超过 0.5 秒的工作者，让主导者对剩余结果进行综合。你需要怎样的可观测性才能知道某个工作者被切断了？
3. 在主导者的综合步骤中加入冲突检测：如果两个工作者返回相互矛盾的答案，主导者应指出分歧而非择一而取。如何在不调用 LLM 的情况下检测矛盾？
4. 阅读 Anthropic 的 Research 系统工程博文。列出三项这个玩具演示要在生产中运行还需要采纳的实践。
5. 对比 LangGraph 的 `create_supervisor`（旧版）和新的工具调用推荐形式。哪种对监督者能看到什么提供了更好的控制？为什么 Anthropic 明确只将子问题答案而非工作者的原始上下文传入综合步骤？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Supervisor（监督者） | "主导智能体" | 负责规划、委派和综合的编排者智能体。自身不执行具体工作。 |
| Worker（工作者） | "子智能体" | 由监督者以窄范围调用、拥有独立上下文窗口的聚焦智能体。 |
| Orchestrator-worker（编排者-工作者） | "监督者模式" | 同一事物的不同叫法，2026 年文献两者均有使用。 |
| Fresh context（全新上下文） | "干净窗口" | 工作者的上下文从其系统提示和指定问题开始，不继承主导者的历史。 |
| Rainbow deployment（彩虹部署） | "渐进发布" | 有状态的长运行智能体需要版本化的"耗尽-替换"策略，而非蓝绿部署。 |
| Token dominance（token 主导） | "上下文是关键变量" | 据 Anthropic 数据，研究评估方差的 80% 来自 token 总用量，而非模型选择。 |
| Scale effort（调配工作量） | "按复杂度匹配智能体数量" | 主导者估算查询难度，相应派遣 1 个或 10 个以上工作者。 |
| Synthesis conflict（综合冲突） | "工作者意见不一" | 两个工作者返回相互矛盾的事实；主导者必须呈现分歧，而非无声地选择一方。 |
