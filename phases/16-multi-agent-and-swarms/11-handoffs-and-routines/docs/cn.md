# 交接与例程——无状态编排（Handoffs and Routines — Stateless Orchestration）

> OpenAI 的 Swarm（2024 年 10 月）将多智能体编排提炼为两个原语：**例程**（指令 + 工具，以系统提示词的形式呈现）和**交接**（一个返回另一个 Agent 的工具）。没有状态机，没有分支 DSL——LLM 通过调用正确的交接工具来完成路由。OpenAI Agents SDK（2025 年 3 月）是其生产级继任者。Swarm 本身依然是最简洁的概念性参考——整个源代码只有几百行。这个模式之所以广泛传播，是因为其 API 接口大约就是"智能体 = 提示词 + 工具；交接 = 返回智能体的函数"。局限性：无状态，因此记忆是调用方的问题。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**前置知识：** Phase 16 · 04（原语模型）  
**预计时间：** 约 60 分钟

## 问题所在

每个多智能体框架都想让你学习它自己的 DSL：LangGraph 的节点和边、CrewAI 的团队和任务、AutoGen 的 GroupChat 和管理者。这些 DSL 确实是真实的抽象，但它们让事情看起来比实际所需的要重得多。

Swarm 推向了相反的方向：使用模型本身已经具备的工具调用能力。交接变成了工具调用。编排者就是当前持有对话的那个智能体。状态机隐含在智能体的系统提示词中。

## 核心概念

### 两个原语

**例程（Routine）。** 定义智能体角色及可用工具的系统提示词。可以把它理解为一组范围化的指令："你是一个分诊智能体；如果用户询问退款，交接给退款智能体。"

**交接（Handoff）。** 智能体可以调用的、返回新 Agent 对象的工具。Swarm 运行时检测到 Agent 返回值后，在下一轮将当前活跃智能体切换为新智能体。

这就是全部的抽象。

```
def transfer_to_refunds():
    return refund_agent  # Swarm 检测到 Agent 返回值 → 切换活跃智能体

triage_agent = Agent(
    name="triage",
    instructions="Route the user to the right specialist.",
    functions=[transfer_to_refunds, transfer_to_sales, transfer_to_support],
)
```

分诊智能体的系统提示词让它根据用户消息选择正确的交接目标。LLM 的工具调用完成路由工作。

### 为什么它广泛传播

- **极小的 API。** 只需学习两个概念。
- **使用模型本已具备的能力。** 工具调用在各提供商中已是生产级成熟功能。
- **无状态机负担。** 你不用描述图；智能体的提示词描述它们会交接给谁。

### 无状态的权衡

Swarm 在运行之间是明确无状态的。框架在一次运行期间维护消息历史，但不持久化任何内容。记忆、连续性、长期运行的任务——全部是调用方的问题。

在生产中（OpenAI Agents SDK，2025 年 3 月），这是主要改变之一：SDK 在保留交接原语的基础上增加了内置的会话管理、护栏和追踪。

### 交接适用的场景

- **分诊模式。** 前线智能体将用户路由到专家。
- **基于技能的交接。** "如果任务需要代码，调用程序员；如果需要研究，调用研究者。"
- **短暂的、边界明确的对话。** 客户支持、FAQ 转工单、简单工作流。

### 交接的局限场景

- **需要共享记忆的长会话。** 交接会将对话状态重置为新智能体的提示词加历史。没有调用方管理的记忆，就没有跨智能体的持久状态。
- **并行执行。** 交接是一次一个的——活跃智能体切换。并行需要调用方协调多个 Swarm 运行。
- **审计与回放。** 无状态运行难以精确回放；LLM 的交接选择不是确定性的。

### OpenAI Agents SDK（2025 年 3 月）

生产级继任者增加了：

- **会话状态。** 跨运行的持久线程。
- **护栏。** 输入/输出验证钩子。
- **追踪。** 每次工具调用和交接都有日志记录。
- **交接过滤器。** 控制交接时传递的上下文内容。

交接原语保留下来了；围绕它增加了生产级的工程便利性。

### Swarm vs GroupChat

两者都使用 LLM 驱动的路由，但它们在**谁决定下一个**上有所不同：

- GroupChat：选择器（函数或 LLM）从外部选取下一个发言者。
- Swarm：当前智能体通过调用交接工具自行选择继任者。

Swarm 是"智能体决定接下来做什么"；GroupChat 是"管理者决定接下来做什么"。Swarm 的决策在活跃智能体的工具调用中；GroupChat 的决策在 `GroupChatManager` 中。

## 构建它

`code/main.py` 从零实现了 Swarm：一个 Agent 数据类、交接机制（工具返回 Agent），以及一个检测智能体切换的运行循环。

演示：一个分诊智能体将用户路由到退款、销售或支持专家。每个专家有自己的工具。运行循环打印每次交接记录。

运行：

```
python3 code/main.py
```

## 使用它

`outputs/skill-handoff-designer.md` 为给定任务设计交接拓扑：存在哪些智能体，它们可以调用哪些交接，以及哪些上下文会随之传递。

## 交付它

检查清单：

- **交接日志记录。** 每次交接写入一个追踪事件，包含来源智能体、目标智能体、上下文快照。
- **上下文传递规则。** 决定交接时传递什么：完整历史（昂贵）、最近 N 条消息，还是摘要。
- **交接上的护栏。** 交接到具有不同工具权限的专家时必须经过验证——否则提示词注入可能强制触发不期望的交接。
- **循环检测。** 两个智能体相互交接是常见失败模式；用简单的最近 K 步环形检查来检测。
- **备用智能体。** 如果交接目标不存在，回退到安全的默认智能体。

## 练习

1. 运行 `code/main.py`，将分诊路由到退款智能体。确认第二轮的活跃智能体是退款智能体。
2. 添加循环检测规则：如果相同两个智能体来回交接了 3 次，强制退出。设计回退方案。
3. 阅读 OpenAI Agents SDK 关于交接过滤器的文档。实现一个"交接时摘要"版本：出站智能体在交接前将上下文压缩为要点摘要，再由入站智能体接管。
4. 对比 Swarm 交接和 GroupChatManager 选择器。哪种模式更容易受到提示词注入的影响？为什么？
5. 阅读 Swarm 食谱（https://developers.openai.com/cookbook/examples/orchestrating_agents）。识别 Swarm 明确做出的一个设计决策，以及 OpenAI Agents SDK 是保留了它还是做了改变。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Routine（例程） | "智能体的提示词" | 系统提示词 + 工具列表。定义角色和可用的交接目标。 |
| Handoff（交接） | "移交给另一个智能体" | 活跃智能体可以调用的、返回新 Agent 的工具。运行时切换活跃智能体。 |
| Stateless（无状态） | "运行之间无记忆" | Swarm 不持久化任何内容；记忆是调用方的责任。 |
| Active agent（活跃智能体） | "现在谁在说话" | 当前持有对话的智能体。交接会改变这一状态。 |
| Context transfer（上下文传递） | "交接时带走什么" | 入站智能体能看到哪些历史的策略：完整、最近 N 条，还是摘要。 |
| Handoff loop（交接循环） | "智能体来回乒乓" | 两个智能体持续相互交接的失效模式。 |
| OpenAI Agents SDK | "生产级 Swarm" | 2025 年 3 月的继任者；在交接原语之上增加了会话、护栏和追踪。 |
| Handoff filter（交接过滤器） | "传递的门控" | SDK 功能，用于在交接边界检查和修改上下文。 |
