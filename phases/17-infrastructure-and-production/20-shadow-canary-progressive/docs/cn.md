# 影子流量、金丝雀发布与 LLM 的渐进式部署（Shadow Traffic, Canary Rollout, and Progressive Deployment for LLMs）

> LLM 发布结合了软件部署中最难的部分：没有单元测试，故障模式分散，信号延迟。顺序是（1）影子模式——将生产请求复制到候选模型，记录日志，对比，对用户零影响；能捕获明显的分布问题，但不是质量保证；（2）金丝雀发布——渐进式流量切换 10% → 25% → 50% → 75% → 100%，每步都有门控；追踪延迟百分位数、每请求成本、错误/拒绝率、输出长度分布、用户反馈率；（3）稳定性确认后针对不同替代方案进行 A/B 测试。非确定性是不可消除的——由于 GPU FP 非结合性加上批次大小方差，相同输入在不同运行间可能有高达 15% 的准确率差异。成本是变量，而非常量——质量提升 20% 的模型每次调用可能贵 3 倍。回滚速度是决定性的：如果回滚需要重新部署，那就太慢了。策略存在于配置/特性标志中；模型存在于有固定摘要的注册表中；回滚 = 翻转策略 + 恢复阈值 + 在数秒内固定旧模型。

**类型：** 学习  
**语言：** Python（标准库，玩具金丝雀进度模拟器）  
**前置知识：** Phase 17 · 13（可观测性）、Phase 17 · 21（A/B 测试）  
**预计时间：** 约 60 分钟

## 学习目标

- 区分影子模式（零影响对比）、金丝雀（实时流量渐进）和 A/B 测试（稳定性确认后的比较）。
- 列举五个 LLM 专属金丝雀指标（延迟、每请求成本、错误/拒绝、输出长度分布、用户反馈）。
- 解释为什么 LLM 非确定性（高达 15%）改变了发布中"稳定"的含义。
- 设计一个以秒计（策略翻转）而非以小时计（重新部署）的回滚路径。

## 问题所在

你发布了一个新模型。离线评估显示 3% 的准确率提升。你在生产中打开它。24 小时内，成本上升 40%，用户点踩增加 8%，三个客户工单报告"奇怪的回答"。你回滚。重新部署需要 3 小时。你的周末毁了。

这一切都是可以避免的。影子模式本可以在任何用户看到之前捕获 40% 的成本峰值。金丝雀本可以在点踩上升时在 10% 处停止。策略标志回滚本可以在 30 秒内完成。这个规范就是填补"离线评估看起来不错"和"真实用户满意"之间差距的东西。

## 核心概念

### 影子模式

候选模型收到与生产相同的请求；输出被记录，不返回给用户。对用户零影响。记录：

- 输出内容（与生产的差异）。
- Token 计数（成本差值）。
- 延迟。
- 拒绝和错误。

能捕获：成本爆炸、长度回归、明显的拒绝变化、硬错误。不能捕获：用户会感知到的质量差值。影子模式是冒烟测试，不是质量测试。

### 金丝雀发布

带门控的渐进式流量切换。典型进度：1% → 10% → 25% → 50% → 75% → 100%。每步对 5 个指标进行门控：

1. **延迟百分位数** — P50、P95、P99。违规：金丝雀的 P99 > 基线的 1.5 倍。
2. **每请求成本** — 混合美元。违规：超过基线 20% 以上。
3. **错误/拒绝率** — 5xx 加显式拒绝。违规：基线的 2 倍。
4. **输出长度分布** — 均值 + P99。违规：分布偏移。
5. **用户反馈率** — 点踩/工单提交。违规：基线的 1.5 倍。

### 非确定性是新的方差

相同输入产生不同输出。原因：

- GPU FP 非结合性（浮点归约顺序因批次而异）。
- 批次大小方差（相同提示词在 128 批次 vs 16 批次中）。
- 采样（温度 > 0）。

测量值：相同评估集上逐次运行准确率差异高达 15%。发布中的"稳定"意味着指标在预期方差范围内，而非与基线相同。将门控设置在噪声水平以上。

### 成本是变量

质量提升 20% 的模型每次调用可能贵 3 倍。每请求成本是五个门控指标之一。发布一个"更好"但打破单位经济性的模型是回滚案例。

### 回滚是武器

- 策略标志（特性标志系统）：在配置中翻转百分比；耗时数秒。
- 模型固定（注册表摘要）：固定模型不会自动升级。
- 回滚 = 恢复标志 + 将固定摘要设置为之前版本。数秒，而非数小时。

如果你的栈需要重新部署才能回滚，在发布之前先修复这个问题。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进式交付控制器。与 Istio/Linkerd 加权路由集成。

**Istio 加权路由** — 服务网格级流量分割。

**KServe / Seldon Core** — 内置金丝雀的模型服务。

**特性标志** — LaunchDarkly、Flagsmith、Unleash。策略级翻转，无需重新部署。

### 指标节奏

金丝雀门控每 5-15 分钟检查一次，取决于流量量。10 req/min 的 1% 流量每窗口给出 50-150 个数据点——对于延迟足够，但对于用户反馈来说噪音较大。10% 给出约 10 倍更多数据。进度应在每步暂停足够长时间以积累足够的样本。

### A/B 步骤是可选的

如果新模型明显不同（不同行为、不同成本曲线、不同语气），在金丝雀通过后在 50% 时进行 A/B 测试。如果它只是改进版本，当金丝雀门控通过时直接跳到 100%。

### 你应该记住的数字

- 金丝雀进度：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：相同输入逐次运行差异高达 15%。
- 五个金丝雀指标：延迟、成本、错误/拒绝、输出长度、用户反馈。
- 成本门控：超过基线 20% 是违规。
- 回滚：数秒，而非数小时。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Shadow mode（影子模式） | "复制到新模型" | 零影响发送给候选模型用于日志记录 |
| Canary（金丝雀） | "渐进式流量" | 带门控的渐进式用户暴露发布 |
| Gates（门控） | "发布检查" | 阻止进度的指标阈值 |
| Non-determinism（非确定性） | "LLM 方差" | 不可消除的逐次运行差异 |
| Policy flag（策略标志） | "标志翻转回滚" | 配置级回滚，数秒而非数小时 |
| Model pin（模型固定） | "注册表摘要" | 对模型版本的不可变引用 |
| Argo Rollouts | "K8s 渐进式" | Kubernetes 原生金丝雀/回滚控制器 |
| KServe | "推理 K8s" | 带金丝雀原语的模型服务 |
| Istio weighted（Istio 加权） | "网格分割" | 服务网格流量分割器 |
