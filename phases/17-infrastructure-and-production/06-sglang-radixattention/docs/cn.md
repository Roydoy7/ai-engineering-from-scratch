# SGLang 与 RadixAttention：前缀密集型工作负载（SGLang and RadixAttention for Prefix-Heavy Workloads）

> SGLang 将 KV 缓存视为存储在基数树中的一等、可复用资源。vLLM 按先来先服务（FCFS）调度请求，而 SGLang 的缓存感知调度器优先处理共享更长前缀的请求——实际上是深度优先的基数树遍历，让热点分支常驻在 HBM 中。在使用 ShareGPT 风格 1K 提示词的 Llama 3.1 8B 上，SGLang 达到约 16200 tok/s，而 vLLM 约为 12500 tok/s，优势约 29%。在前缀密集的 RAG 工作负载上，优势达到 6.4 倍。在语音克隆形状的工作负载上，缓存命中率超过 86%。2026 年在 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS 上部署于 40 万以上 GPU。坑点是：当前缀顺序不一致时，6.4 倍的数字会消失——顺序是工程师的杠杆。

**类型：** 学习  
**语言：** Python（标准库，玩具基数树缓存 + 缓存感知调度器）  
**前置知识：** Phase 17 · 04（vLLM 服务内部原理）、Phase 14（智能体 RAG）  
**预计时间：** 约 75 分钟

## 学习目标

- 画出 RadixAttention：前缀如何存储在基数树中，以及 KV 块如何在根植于同一分支的序列间共享。
- 解释缓存感知调度，以及为什么 FCFS 对前缀密集型流量是错误的。
- 给定前缀缓存命中率和提示词长度分布，计算工作负载的预期加速比。
- 说出使 6.4 倍数字成为现实的提示词排序规范，以及不遵守时会失去的上行空间。

## 问题所在

经典服务将每个请求的提示词视为不透明的。即使 5000 个 RAG 请求都以相同的 2000 token 系统提示加相同的检索序言开头，vLLM 也会将那 2000 token 的前缀预填充 5000 次。GPU 一遍又一遍地做同样的工作。

观察：智能体和 RAG 工作负载中的提示词几乎总是共享长前缀。系统提示、工具 schema、少样本示例、检索头、对话历史——所有这些在请求间重复出现。如果你将该前缀的 KV 缓存存储一次并复用，就不需要再次预填充它。

RadixAttention 正是这样做的。Token 被索引在基数树中；每个节点拥有从根到该节点路径上的 token 序列对应的 KV 块。新请求遍历树：任何匹配 token 的节点都复用该节点的 KV 块。预填充成本变得与"新"后缀成正比，而非完整提示词。

挑战在于调度。如果两个请求共享 2000 token 的前缀，而第三个只共享同一前缀的 200 个 token，你希望将前两个长共享请求一起服务，让长前缀保持在 HBM 中。FCFS 恰恰相反——它先服务最先到达的请求，可能在下一个长前缀请求到来之前就驱逐了热点分支。

## 核心概念

### 基数树作为 KV 索引

基数树（紧凑前缀树）存储 token 序列。每个节点拥有一段 token 范围以及为该范围计算的 KV 块。子节点将序列延伸一个或多个 token。

```
根节点
 |- "你是一个有用的助手..."  （2000 个 token，124 个 KV 块）
      |- "上下文：<文档 A>..."  （500 个 token，31 个块）
           |- "问题：Alice..."  （80 个 token，5 个块）
           |- "问题：Bob..."    （95 个 token，6 个块）
      |- "上下文：<文档 B>..."  （520 个 token，33 个块）
```

一个新请求带着系统提示 + "上下文：<文档 A>" + "问题：Carol" 到来。调度器遍历：系统前缀匹配（124 个块复用），文档 A 分支匹配（31 个块复用），然后只为"问题：Carol"分配新块（4 个块）。预填充成本：4 个块的新 token。没有树：160 个块。约 40 倍的预填充节省。

### 缓存感知调度

基数树支持的复用在缓存频繁置换时毫无意义。两个关键策略：

1. **深度优先分配**。从队列中选择下一个请求时，优先选择与当前运行集合根植于同一分支的请求。这让热点分支保持驻留。
2. **分支级 LRU，而非块级 LRU**。驱逐整个分支（从使用最少的叶节点开始），而非单个块，让缓存形状与基数树形状匹配。

FCFS 违反了这两条规则。共享 2000 个 token 的请求排在共享 50 个 token 的请求后面，然后 2000 token 分支被驱逐为后者腾出空间。

### 你应该记住的基准数字

- Llama 3.1 8B，H100，ShareGPT 1K 提示词：SGLang 约 16200 tok/s vs vLLM 约 12500（约 29% 优势）。
- 前缀密集的 RAG（相同系统 + 相同文档，问题各异）：SGLang 上高达 6.4 倍。
- 语音克隆工作负载：86.4% 前缀缓存命中率。
- SGLang 客户的生产命中率：50-99%，取决于提示词规范。
- 2026 年部署于 40 万以上 GPU。

### 排序坑点

6.4 倍的数字依赖于一致的提示词模板排序。如果你的客户端在某些请求中按 `[系统, 工具, 上下文, 历史, 问题]` 顺序构造提示词，而在其他请求中按 `[系统, 上下文, 工具, 历史, 问题]`，树就找不到共享前缀。对人类来说看起来是共享前缀的内容，对基数树来说是两个不同的序列。

工程师的杠杆：你的提示词模板就是缓存键。固定顺序。将所有不可变内容（系统、工具、schema）放在最前面。将检索上下文放在其次。将用户问题放在最后。不要将动态内容穿插到前缀中。

研究中的真实案例：将动态内容移出可缓存前缀，一次部署的缓存命中率从 7% 提升到 74%。

### RadixAttention 的胜负场景

胜出场景：
- RAG（相同检索序言，问题各异）。
- 智能体（相同工具 schema，查询各异）。
- 带有长系统提示的对话。
- 带有重复序言的语音/视觉工作负载。

失去优势（回到 vLLM 级别吞吐量）：
- 使用唯一提示词的单次生成（代码补全、无系统提示的开放式对话）。
- 每个请求都将唯一内容穿插到前缀中的动态提示词。

### 为什么这是调度器问题，而非仅仅是内核问题

你可以将 KV 复用实现为内核技巧。SGLang 的洞察是：只有调度器将热点分支保持常驻，复用才有价值。朴素的"可用则复用"策略在混合负载下会使缓存频繁置换。基数树索引调度器是将内核技巧转化为 29% 生产优势的关键。

### 与 vLLM 的相互关系

两个系统不是严格竞争关系。2026 年，vLLM 添加了前缀缓存（`--enable-prefix-caching`）和缓存感知路由器（Rust 版 vLLM Router）。差距缩小但没有完全消失——SGLang 的整个栈是基数优先的；vLLM 是嫁接上去的。对于以前缀复用为主的工作负载，SGLang 仍然是默认选择。对于没有强前缀模式的通用服务，vLLM 不相上下甚至更好。

## 使用它

`code/main.py` 实现了一个玩具基数树 KV 缓存加上两种策略的调度器：FCFS 和缓存感知。在相同工作负载上运行两者，报告前缀缓存命中率和吞吐量差距。然后运行"顺序打乱"工作负载，展示 6.4 倍的崩溃。

## 交付它

本课产出 `outputs/skill-radix-scheduler-advisor.md`。给定工作负载描述（提示词模板形状、检索模式、并发租户数），它产出提示词排序处方以及 SGLang 采用的通过/不通过决策。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| RadixAttention | "SGLang 的东西" | KV 缓存索引为基数树，让共享前缀复用块 |
| Radix tree（基数树） | "紧凑前缀树" | 每个节点拥有一段 token 范围及其 KV 块的树 |
| Cache-aware scheduler（缓存感知调度器） | "热点分支优先" | 优先处理共享常驻分支请求的调度器 |
| Prefix-cache hit rate（前缀缓存命中率） | "你的提示词有多少是免费的" | 从复用 KV 块服务的提示词 token 比例 |
| FCFS | "先来先服务" | 破坏前缀局部性的默认调度策略 |
| Branch-level LRU（分支级 LRU） | "驱逐叶节点" | 与基数形状匹配的驱逐策略 |
| Prompt template ordering（提示词模板排序） | "缓存键" | 提示词组件顺序决定树能共享什么 |
| System prompt pinning（系统提示固定） | "常驻前缀" | 保持不可变的系统部分常驻以避免驱逐抖动 |
