# 批处理 API——50% 折扣作为行业标准（Batch APIs — the 50% Discount as Industry Standard）

> 每家主要供应商都提供异步批处理 API，享有 50% 折扣和约 24 小时周期。OpenAI、Anthropic、Google 以及大多数推理平台（Fireworks 批处理层、Together 批处理）实现了相同的模式。叠加批处理与提示词缓存，夜间管道的成本可降至同步非缓存成本的约 10%。规则非常简单粗暴：如果不是交互式的，就应该用批处理。内容生成管道、文档分类、数据提取、报告生成、批量标注、目录标记——任何可以接受 24 小时延迟的工作负载，在迁移到批处理之前都在白白浪费金钱。2026 年的生产模式是将每个新的 LLM 工作负载分流到三条通道：交互式（同步加缓存）、半交互式（带备用的异步队列）、批处理（夜间，叠加缓存输入）。假装是交互式但实际上可以容忍数分钟延迟的工作负载浪费最多。

**类型：** 学习  
**语言：** Python（标准库，玩具批处理与同步成本模拟器）  
**前置知识：** Phase 17 · 14（提示词与语义缓存）  
**预计时间：** 约 45 分钟

## 学习目标

- 说出三家供应商的批处理 API（OpenAI、Anthropic、Google）以及通用的 50% 折扣 + 24 小时周期保证。
- 计算在夜间分类工作负载上叠加批处理 + 缓存输入的成本，并与同步非缓存基线比较。
- 将工作负载分流到交互式/半交互式/批处理，并论证选择的通道。
- 说出两个陷阱：部分交互性（用户期望比 24 小时更快）和输出 schema 漂移（批处理文件格式因供应商而异）。

## 问题所在

你的团队部署了夜间报告生成管道。5 万个文档，每个摘要，聚类摘要，起草执行简报。同步运行需要 4 小时，每晚 2000 美元。你听说了批处理 API。

批处理让你节省 50%。你还对系统提示词（5 万次调用共享）启用了提示词缓存。叠加后，账单降至每晚 180 美元——约为基线的 9%。同一管道，三个配置更改。

批处理是 LLM 成本工具箱中最便宜但没人使用的杠杆。原因主要是组织上的：团队认为"实时"，而 SLA 实际上是"到早上"。本课是关于不把 90% 的账单留在桌上。

## 核心概念

### 三个批处理 API

**OpenAI Batch API**：上传包含请求列表的 JSONL 文件。承诺 24 小时周期（实际通常 2-8 小时）。输入和输出 token 享 50% 折扣。`/v1/batches` 端点。符合条件的缓存输入还可以额外享受缓存输入定价。

**Anthropic Message Batches**：JSONL 上传。24 小时周期。50% 折扣。支持 `cache_control`——缓存写入是显式的，读取在批次中自动发生。

**Google Vertex AI 批量预测**：BigQuery 或 GCS 输入。Gemini 享有类似 50% 折扣。与 Vertex 管道集成。

### 语义上：异步不等于慢

批处理意味着"我承诺在 24 小时内返回"——而非"这将花费 24 小时"。典型 P50 是 2-6 小时。供应商在 GPU 库存利用率不足的非高峰窗口调度你的批次。

### 与缓存叠加

5 万个文档摘要，共享同一个 4K token 系统提示词：

- 同步非缓存：50000 × (输入价格 × 4000 + 输出价格 × 200) 按全价。
- 同步缓存：第一次写入后系统提示词被缓存；其余 49999 次获得 10 倍便宜的输入价格。
- 批处理加缓存：以上所有加上读取和写入均享 50% 折扣。

叠加：批处理 + 缓存 = 同步非缓存账单的约 10%。任何夜间运行且有共享系统提示词的工作负载都应该使用这个组合。

### 工作负载分流

**交互式** — 用户等待响应。TTFT 很重要。同步调用加提示词缓存。不能批处理。

**半交互式** — 用户提交任务，几分钟后检查结果。带备用的异步队列，在批处理不可用时回退到同步。想想中等规模的 RAG 索引。

**批处理** — 用户期望"到早上"或"下一个小时"的结果。内容管道、规模化分类、离线分析。始终批处理，始终叠加缓存。

常见错误：因为管道是生产级别的就将所有东西归类为交互式。生产级别不是延迟规格——SLA 才是。

### 部分交互性陷阱

有些功能看起来是交互式的，但可以接受 5-10 分钟。示例：带"刷新"按钮的每夜客户健康报告。用户点击刷新；等待 10 分钟可以接受。团队将其部署为同步。50 个并发刷新的成本是批处理后通过邮件发送的 10 倍。

要问的问题："对这个用户来说，24 小时意味着什么？"如果答案是"他们不会注意到"，那就批处理。

### 输出 schema 陷阱

批处理文件格式因供应商而异：

- OpenAI：JSONL，每行一个请求。
- Anthropic：JSONL，每行一条消息；响应格式内嵌。
- Vertex：BigQuery 表或带 TFRecord 的 GCS 前缀。

编写"一个批处理客户端"跨多个供应商意味着每个供应商都需要适配器代码。宣传多供应商批处理的网关（Portkey、LiteLLM 部分层级）仍然是对原始格式的薄封装。

### 你应该记住的数字

- 跨供应商的批处理折扣：输入 + 输出均享 50% 固定折扣。
- 周期 SLA：保证 24 小时，典型 P50 为 2-6 小时。
- 叠加批处理 + 缓存输入：同步非缓存成本的约 10%。
- 工作负载分流规则：如果可以接受 24 小时延迟，始终使用批处理。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Batch API（批处理 API） | "异步折扣" | 24 小时周期享 50% 折扣 |
| JSONL | "批处理格式" | 每行一个 JSON 请求；OpenAI/Anthropic 标准 |
| Message Batches | "Anthropic 批处理" | Anthropic 的批处理 API 产品名称 |
| Batch prediction（批量预测） | "Vertex 批处理" | Vertex AI 的批处理 API 产品 |
| Turnaround SLA（周期 SLA） | "24 小时承诺" | 保证，而非典型值；典型值为 2-6 小时 |
| Workload triage（工作负载分流） | "交互性决策" | 交互式/半交互式/批处理路由决策 |
| Output schema（输出 schema） | "响应格式" | 每供应商的 JSONL 布局；不可移植 |
| Stacked discount（叠加折扣） | "批处理 + 缓存" | 两者均适用时约为非缓存同步账单的 10% |
