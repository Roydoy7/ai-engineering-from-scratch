# LLM 的 FinOps——单位经济学与多租户归因（FinOps for LLMs — Unit Economics and Multi-Tenant Attribution）

> 传统 FinOps 在 LLM 支出上失效。成本是 token 交易，而非资源运行时间。标签无法映射——API 调用是交易，不是资产。工程决策（提示词设计、上下文窗口、输出长度）就是财务决策。2026 年的操作手册有三个归因维度需要在第一天就进行监控：按用户（`user_id`）用于座位定价和扩展，按任务（`task_id` + `route`）用于产品界面成本和优先级，按租户（`tenant_id`）用于单位经济学和续签。四个 token 层——提示词、工具、记忆、响应——任何一个桶都会隐藏支出。多租户产品的执行梯度：按租户速率限制（预期峰值的 2-3 倍，清晰的 429 + 重试时间）；每日支出上限（合同上限的 1.5-3 倍；触发速率收紧 + 告警）；在支出 z 分数 > 4 时的停止开关（自动暂停 + 呼叫值班人员）。归因模式：标签聚合、遥测连接器（追踪 ID → 账单；最高准确率）、采样外推、基于模型的分配、事件溯源、实时流式传输。单位指标：每个已解决查询的成本，每个生成工件的成本——而非每百万 token 美元数。事后标记总会有遗漏；在请求创建时进行监控。

**类型：** 学习  
**语言：** Python（标准库，带停止开关的玩具成本归因模拟器）  
**前置知识：** Phase 17 · 13（可观测性）、Phase 17 · 14（缓存）  
**预计时间：** 约 60 分钟

## 学习目标

- 解释为什么传统 FinOps（标签 + 层级）在 LLM 支出上失效，并说出三个新的归因维度。
- 列举四个 token 层（提示词、工具、记忆、响应），以及为什么单一桶计费会隐藏成本。
- 为多租户产品设计执行梯度（速率限制 → 支出上限 → 停止开关）。
- 选择单位指标（每个已解决查询/工件的成本），而非每百万 token 美元数。

## 问题所在

你的账单显示 4 万美元。你不知道：
- 哪个租户花了这笔钱。
- 哪个产品功能驱动了它。
- 是否有任何单个用户在滥用。
- 提示词膨胀、工具调用还是记忆放大是罪魁祸首。

供应商端的标签聚合适用于云资源（EC2、S3），标签传播到行项目。LLM API 调用不会自动添加标签——你必须在调用点上打上用户/任务/租户的印记并贯穿始终。事后归因总是会遗漏边缘情况。

## 核心概念

### 三个归因维度

**按用户**（`user_id`）：谁花了什么。驱动座位定价、扩展对话，识别高消耗用户。

**按任务**（`task_id` + `route`）：哪个产品界面花了什么。驱动功能优先级、停止高成本功能的决策。

**按租户**（`tenant_id`）：哪个客户有盈利性。驱动单位经济学、续签定价、层级门槛。

在第一天就在调用点监控所有三者。事后归因总是更差。

### 四个 token 层

| 层 | 示例 | 占总量典型百分比 |
|----|------|----------------|
| 提示词 | 系统提示词 + 用户输入 | 40-60% |
| 工具 | 反馈的工具调用结果 | 20-40%（智能体工作负载） |
| 记忆 | 先前对话/检索的文档 | 10-30% |
| 响应 | 模型输出 | 10-30% |

将所有四层放入一个桶中使优化变成盲目的。在你的归因 schema 中将它们分开。

### 执行梯度

1. **速率限制**（按租户）。预期峰值的 2-3 倍。返回带 `Retry-After` 的 429。租户感受到阻力；没有意外账单。

2. **每日支出上限**（按租户）。合同上限的 1.5-3 倍。触发：收紧速率限制 + 告警客户成功团队。

3. **停止开关**（当支出 z 分数 > 4 时，相对于租户基线）。自动暂停租户；呼叫值班人员；上升至运维 + 客户成功团队。

### 归因模式

- **标签聚合**：在元数据头中打印记；之后聚合。简单；粗略。
- **遥测连接器**：通过追踪 ID 将追踪与账单连接。最高准确率。成熟团队所做的。
- **采样 + 外推**：采样 5-10%，乘以倍数。粗略支出的高性价比方案；会错过尾部。
- **基于模型的分配**：回归推断成本驱动因素。用于没有标签的遗留数据。
- **事件溯源**：成本作为流中的事件（Kafka / Kinesis）。实时。
- **实时流式传输**：仪表板亚秒级更新。

### 每 X 的成本是单位指标

每百万 token 美元数是供应商语言。产品指标：

- 每个已解决支持工单的成本。
- 每篇生成文章的成本。
- 每个成功智能体任务的成本。
- 每用户会话分钟的成本。

将成本与产品结果挂钩。否则优化是无锚的。

### 成本归因追踪形态

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

在每次调用时发送。存储在数据湖中。按维度聚合。Phase 17 · 13 可观测性栈就是它的存放地。

### 叠加节省栈

叠加：缓存 + 批处理 + 路由 + 网关。四者全部叠加：
- L2 缓存（Phase 17 · 14）：输入便宜约 10 倍。
- 批处理（Phase 17 · 15）：50% 折扣。
- 路由到廉价模型（Phase 17 · 16）：成本减少 60%。
- 网关效率（Phase 17 · 19）：冗余 + 重试。

最优叠加：朴素基线的约 5-10%。大多数团队有 2-3 个杠杆；很少能叠加全部四个。

### 你应该记住的数字

- 归因维度：按用户、按任务、按租户。
- 四个 token 层：提示词、工具、记忆、响应。
- 停止开关：支出 z 分数 > 4。
- 单位指标：每个已解决查询的成本，而非每百万 token 美元数。
- 叠加优化：基线的约 5-10% 是可能的。

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| Per-user attribution（按用户归因） | "用户级成本" | 每次调用都打上 `user_id` 印记 |
| Per-task attribution（按任务归因） | "功能成本" | `task_id` + `route` 识别产品界面 |
| Per-tenant attribution（按租户归因） | "客户成本" | `tenant_id`；驱动单位经济学 |
| Four token layers（四个 token 层） | "成本层" | 提示词 + 工具 + 记忆 + 响应 |
| Rate limit（速率限制） | "429 守护" | 在网关处执行的按租户上限 |
| Daily spend cap（每日支出上限） | "每日上限" | 带告警的租户范围预算 |
| Kill switch（停止开关） | "自动暂停" | 支出 z 分数 > 4 触发自动暂停 |
| Cost per resolved（每已解决成本） | "产品单位指标" | 与产品结果而非 token 挂钩的成本 |
| Telemetry joiner（遥测连接器） | "追踪到账单" | 最高准确率的归因模式 |
| Stacked optimization（叠加优化） | "缓存+批处理+路由+网关" | 叠加节省至约 5-10% 基线 |
