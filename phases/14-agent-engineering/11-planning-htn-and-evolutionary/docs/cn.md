# HTN 规划与进化搜索（Planning with HTN and Evolutionary Search）

> 符号规划处理计划可证明正确的情况。进化代码搜索处理适应度函数可被机器验证的情况。ChatHTN（2025）和 AlphaEvolve（2025）展示了当与 LLM 结合时，各自能解锁什么。

**类型：** 构建  
**语言：** Python（标准库）  
**前置知识：** Phase 14 · 02（ReWOO 与规划-执行）  
**预计时间：** 约 75 分钟

## 学习目标

- 解释层次任务网络（HTN）：任务、方法、算子、前置条件、效果。
- 描述 ChatHTN 的混合循环——带 LLM 回退分解的符号搜索。
- 解释 AlphaEvolve 的进化循环，以及为什么它只能在有程序化评估器的情况下工作。
- 用标准库实现一个玩具 HTN 规划器和一个玩具进化搜索。

## 问题所在

ReWOO（第 02 课）、规划-执行和 ReAct 覆盖了大多数智能体规划场景。有两种情况它们处理得不好：

1. **具有可证明正确性的计划。** 调度、航路规划、合规工作流——计划必须通过构造来保证正确。偶尔会幻觉出一个步骤的流畅 LLM 计划是不可接受的。
2. **具有机器可验证适应度函数的优化。** 矩阵乘法、调度启发式、编译器过程——目标不是"一个正确的计划"，而是"最佳的计划"。

HTN 规划和 AlphaEvolve 解决了这两个不同的问题。两者都将 LLM 作为放大器，而非替代者。

## 核心概念

### 层次任务网络（HTN）

HTN 包含：

- **任务（Tasks）** — 复合任务（需要分解）和原语任务（直接可执行）。
- **方法（Methods）** — 将复合任务分解为子任务的方式，带有前置条件。
- **算子（Operators）** — 带有前置条件和效果的原语动作。
- **状态（State）** — 一组事实。

规划：给定目标任务和初始状态，找到分解为前置条件按序满足的原语算子的方案。

HTN 比 LLM 更早出现，至今仍是可证明正确计划的参考标准。

### ChatHTN（Gopalakrishnan 等人，2025）

ChatHTN（arXiv:2505.11814）将符号 HTN 与 LLM 查询交替进行：

1. 尝试用现有方法分解当前复合任务。
2. 如果没有方法适用，询问 LLM："在状态 `s` 下你会如何分解 `task`？"
3. 将 LLM 的响应翻译为候选子任务。
4. 对照算子模式验证；拒绝无效的分解。
5. 递归。

论文的核心主张：生成的每个计划都是可证明正确的，因为 LLM 建议仅作为候选分解进入，而非直接编辑计划。符号层拥有正确性；LLM 扩展方法库。

在线方法学习（OpenReview `gwYEDY9j2x`，2025 年后续工作）添加了一个通过回归泛化 LLM 生成的分解的学习器——将 LLM 查询频率降低高达 75%。

### AlphaEvolve（Novikov 等人，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是另一回事：由 Gemini 2.0 Flash/Pro 集成编排的进化代码搜索。

循环：

1. 以种子程序 + 程序化评估器（返回适应度分数）开始。
2. LLM 集成提议变异。
3. 通过评估器运行变异。
4. 保留最好的；再次变异。

已发布的成果：

- 56 年来首次改进 4x4 复杂矩阵乘法的 Strassen 算法（48 次标量乘法）。
- 通过 Borg 调度启发式恢复 0.7% 的谷歌计算资源。
- 在前沿工作负载上 FlashAttention 加速 32%。

硬性约束：适应度函数必须是机器可验证的。对散文答案的进化搜索不会收敛。

### 何时使用哪种方法

| 问题类别 | 使用 | 原因 |
|----------|------|------|
| 带硬约束的调度 | HTN + ChatHTN | 可证明的正确性 |
| 编译器优化 | AlphaEvolve | 机器可验证的适应度 |
| 多步骤任务执行 | ReAct / ReWOO | LLM 在循环中，无形式保证 |
| 带测试的代码改进 | AlphaEvolve | 测试即评估器 |
| 策略绑定自动化 | HTN | 前置条件编码策略 |

### 这个模式在哪里出错

- **没有算子的 HTN。** 没有前置条件/效果模式，正确性声明就会崩溃。ChatHTN 的"LLM 建议分解"要求模式拒绝无效的移动。
- **没有真正评估器的 AlphaEvolve。** "询问 LLM 代码是否更好"不是适应度函数。评估器必须是确定性的且快速的。
- **过度工程化。** 大多数智能体任务不需要这两者。先使用 ReAct 或 ReWOO。

## 构建它

`code/main.py` 实现了两个玩具：

- 一个标准库 HTN 规划器，带有算子、方法、前置条件、效果，以及当没有方法匹配复合任务时触发的 `LLMFallback`。"LLM"是一个脚本化分解器，使规划器可以离线运行。
- 一个对算术程序的标准库进化搜索：生成输出在测试集上最小化 `|f(x) - target|` 的表达式。评估器是确定性的。

运行：

```
python3 code/main.py
```

追踪显示 HTN 规划器分解一个复合任务（带有规划中途的 LLM 回退），以及进化循环收敛到目标表达式。

## 使用它

- **HTN 规划器** — `pyhop`、`SHOP3`，或为特定领域的策略执行自行构建。
- **ChatHTN** — 研究代码；模式（符号 + LLM 回退）可以移植到任何 HTN 规划器。
- **AlphaEvolve** — DeepMind 论文；模式（集成 + 评估器）是可复现的。OpenEvolve 和类似的开源分支正在涌现。
- **智能体框架** — 目前没有一个框架原生支持 HTN 或 AlphaEvolve。将其构建为子智能体或后台工作者。

## 交付它

`outputs/skill-hybrid-planner.md` 生成一个混合规划器脚手架（HTN 或进化），LLM 的角色被明确限定范围。

## 练习

1. 用回溯扩展 HTN 规划器：当算子的后置条件在运行时失败时，回滚并尝试下一个方法。
2. 向 ChatHTN 添加 LLM 方法缓存：当 LLM 在状态模式 `P` 中分解任务 `T` 时，存储结果。下次调用时先检查方法库。
3. 将进化搜索评估器替换为真实的测试套件。进化出一个通过 20 个测试用例的排序函数；报告收敛所需的代数。
4. 阅读 AlphaEvolve 的评估器设计说明。为你关心的领域设计一个评估器（SQL 查询优化、测试套件最小化、部署 YAML）。
5. 组合使用：用 HTN 将复合任务分解为子任务，然后对每个子任务的原语算子使用进化搜索。它在哪里表现出色，在哪里是过度工程化？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| HTN | "层次规划器" | 带算子、前置条件、效果的任务分解。 |
| 方法（Method） | "分解规则" | 将复合任务分解为子任务的方式。 |
| 算子（Operator） | "原语动作" | 带前置条件和效果的具体步骤。 |
| ChatHTN | "LLM + HTN" | 当没有方法匹配时，符号规划器询问 LLM。 |
| AlphaEvolve | "进化代码搜索" | 集成 LLM 变异代码；确定性评估器选择。 |
| 适应度函数（Fitness function） | "评估器" | 对输出的确定性、机器可验证的评分。 |
| 在线方法学习（Online method learning） | "缓存的 LLM 分解" | 存储并泛化 LLM 计划以降低查询成本。 |
