# 工具使用与函数调用（Tool Use and Function Calling）

> Toolformer（Schick 等人，2023）开创了自监督工具标注。伯克利函数调用排行榜 V4（Patil 等人，2025）设定了 2026 年的基准：40% 智能体类、30% 多轮次、10% 实时、10% 非实时、10% 幻觉检测。单轮已基本解决，记忆、动态决策和长序列工具链尚未解决。

**类型：** 构建  
**语言：** Python（标准库）  
**前置知识：** Phase 14 · 01（智能体循环）、Phase 13 · 01（函数调用深度解析）  
**预计时间：** 约 60 分钟

## 学习目标

- 解释 Toolformer 的自监督训练信号：只有当工具执行结果降低下一个 token 的损失时，才保留工具标注。
- 列出 BFCL V4 的五个评估类别及各自的衡量内容。
- 用标准库实现一个带有模式验证、参数强制转换和执行沙箱的工具注册表。
- 诊断 2026 年三个尚未解决的问题：长序列工具链、动态决策和记忆。

## 问题所在

早期的工具使用问的是：模型能预测正确的函数调用吗？现代工具使用问的是：模型能在 40 步中链式调用工具，同时维持记忆、处理部分可观测性、从工具失败中恢复、不幻觉出不存在的工具吗？

Toolformer 建立了基线：模型可以通过自监督学习到何时调用工具。BFCL V4 定义了 2026 年的评估目标。两者之间的差距，正是生产智能体所处的空间。

## 核心概念

### Toolformer（Schick 等人，NeurIPS 2023）

思路：让模型用候选 API 调用标注自己的预训练语料库。对每个候选，执行它。只有当包含工具结果能降低下一个 token 的损失时，才保留该标注。在过滤后的语料库上进行微调。

涵盖的工具：计算器、问答系统、搜索引擎、翻译器、日历。自监督信号完全基于工具是否有助于预测文本——无需人工标签。

规模结论：工具使用在规模上涌现。较小的模型因工具标注而受损；较大的模型从中获益。这就是为什么 2026 年的前沿模型内置了强大的工具使用能力，而大多数 7B 模型需要显式的工具使用微调才能可靠工作。

### 伯克利函数调用排行榜 V4（Patil 等人，ICML 2025）

BFCL 是 2026 年事实上的评估标准。V4 组成：

- **智能体类（40%）** — 完整的智能体轨迹：记忆、多轮次、动态决策。
- **多轮次（30%）** — 带工具链的交互式对话。
- **实时（10%）** — 用户提交的真实提示（更难的分布）。
- **非实时（10%）** — 合成测试用例。
- **幻觉（10%）** — 检测何时不应该调用工具。

V3 引入了基于状态的评估：工具序列执行后，检查 API 的实际状态（如"文件是否已创建？"），而不是匹配工具调用的 AST。V4 增加了网页搜索、记忆和格式敏感性类别。

2026 年关键发现：单轮函数调用接近解决。失败集中在记忆（跨轮次携带上下文）、动态决策（根据先前结果选择工具）、长序列链（超过 20 步后漂移）和幻觉检测（在没有合适工具时拒绝调用）。

### 工具模式

每个提供商都有自己的模式。细节有所不同，但形状相同：

```
name: string
description: string（功能说明，以及何时使用）
input_schema: JSON Schema（属性、必需项、类型、枚举）
```

Anthropic 直接使用 `input_schema`。OpenAI 使用 `function.parameters`。两者都接受 JSON Schema。描述是承重的部分——模型读取描述来选择正确的工具。糟糕的工具描述是工具选择错误失败的 #1 根本原因。

### 参数验证

永远不要信任工具调用。验证以下内容：

1. **类型强制转换。** 模型可能在模式要求 int 时返回字符串 "5"。如果无歧义则强制转换；否则拒绝。
2. **枚举验证。** 如果模式要求 `status in {"open", "closed"}` 而模型输出 `"in_progress"`，拒绝并返回描述性错误。
3. **必需字段。** 缺失必需字段 -> 立即将错误观察返回给模型，而不是崩溃。
4. **格式验证。** 日期、邮件、URL——使用具体解析器验证，而不是正则表达式。

每次验证失败都应返回一个结构化观察，使模型能以正确的形式重试。

### 并行工具调用

现代提供商支持在一个助手轮次中进行并行工具调用。循环：

1. 模型输出 3 个具有不同 `tool_use_id` 的工具调用。
2. 运行时执行它们（如果独立则并行）。
3. 每个结果作为 `tool_result` 块通过 `tool_use_id` 关联返回。

工程规则：将关联 ID 视为承重的部分。交换它们会导致错误的工具到错误结果的路由。

### 沙箱

工具执行是沙箱边界。详见第 09 课。简短版本：每个工具应指定读/写接口、网络访问、超时和内存上限。通用的 `run_shell(cmd)` 是危险信号；具体的 `git_status()` 更安全。

## 构建它

`code/main.py` 实现了一个生产形态的工具注册表：

- JSON Schema 子集验证器（仅标准库）。
- 带描述、输入模式、超时和执行器的工具注册。
- 参数强制转换和枚举验证。
- 带关联 ID 的并行工具分发。
- 作为结构化字符串的错误观察。

运行：

```
python3 code/main.py
```

追踪显示一个小型智能体在一个轮次中调用三个工具，其中一个被故意格式错误的调用被拒绝，并返回模型可以处理的描述性错误。

## 使用它

每个提供商都有自己的工具模式——Anthropic、OpenAI、Gemini、Bedrock。如果需要多提供商支持，使用翻译层（OpenAI Agents SDK、Vercel AI SDK、LangChain 工具适配器）。BFCL 是参考基准——如果工具使用是产品的核心，在发布前对你的智能体运行它。

## 交付它

`outputs/skill-tool-registry.md` 为给定任务领域生成工具目录、模式和注册表。包含描述质量检查（每个工具的描述是否告知模型何时使用它？）。

## 练习

1. 添加一个让模型明确拒绝使用任何其他工具的"无操作"工具。在类似 BFCL 的幻觉测试中进行测量。
2. 为 int-as-string 和 float-as-string 实现参数强制转换。强制转换在哪个点开始隐藏真正的 bug？
3. 添加每工具超时和熔断器（连续 3 次失败后拒绝该工具 60 秒）。这对模型的恢复方式有什么影响？
4. 阅读 BFCL V4 描述。选择一个类别（如"多轮次"）并通过你的智能体运行 10 个示例提示。报告通过率。
5. 将标准库验证器移植到 Pydantic 或 Zod。Pydantic/Zod 捕获了玩具遗漏的什么？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| 函数调用（Function calling） | "工具使用" | 带有验证模式的结构化输出工具调用。 |
| Toolformer | "自监督工具标注" | Schick 2023——保留使结果降低下一个 token 损失的工具调用。 |
| BFCL | "伯克利函数调用排行榜" | 2026 年基准：40% 智能体类、30% 多轮次、10% 实时、10% 非实时、10% 幻觉。 |
| 工具模式（Tool schema） | "模型的函数签名" | 名称、描述、参数的 JSON Schema。 |
| tool_use_id | "关联 ID" | 将工具调用与其结果关联；并行分发的关键。 |
| 幻觉检测（Hallucination detection） | "知道何时不调用" | V4 类别：在没有合适工具时拒绝调用。 |
| 参数强制转换（Argument coercion） | "字符串转整数修复" | 针对可预测的模式不匹配的窄修复；有歧义时拒绝。 |
| 沙箱（Sandboxing） | "工具执行边界" | 每工具的读/写接口、网络、超时、内存上限。 |
