# 记忆：虚拟上下文与 MemGPT（Memory: Virtual Context and MemGPT）

> 上下文窗口是有限的。对话、文档和工具追踪则不是。MemGPT（Packer 等人，2023）将其比作操作系统的虚拟内存——主上下文是内存（RAM），外部存储是磁盘，智能体在二者之间换页。这是 2026 年所有记忆系统继承的模式。

**类型：** 构建  
**语言：** Python（标准库）  
**前置知识：** Phase 14 · 01（智能体循环）、Phase 14 · 06（工具使用）  
**预计时间：** 约 75 分钟

## 学习目标

- 解释 MemGPT 所依托的操作系统类比：主上下文 = 内存，外部上下文 = 磁盘，记忆工具 = 换入/换出。
- 用标准库实现 MemGPT 的双层模式，包含主上下文缓冲区、可搜索的外部存储和换入/换出工具。
- 描述智能体如何发出"中断"来查询或修改外部记忆，以及结果如何拼接回下一个提示中。
- 识别 MemGPT 的设计选择如何延续到 Letta（第 08 课）和 Mem0（第 09 课）中。

## 问题所在

上下文窗口看起来应该能解决记忆问题。事实并非如此。生产中反复出现三种失败模式：

1. **溢出。** 多轮次对话、长文档或工具调用密集的轨迹超出窗口。截止点之后的一切都消失了。
2. **稀释。** 即使在窗口内，塞入无关上下文也会稀释注意力在关键内容上的分配。前沿模型在长输入上仍然会退化。
3. **持久性。** 新会话以空窗口开始。没有外部记忆的智能体无法跨会话说"记得你之前让我……"。

更大的窗口有帮助，但无法从根本上解决这个问题。Mem0 2025 年的论文测量显示，128k 窗口的基线在长序列事实上仍然失败，而拥有外部记忆的 4k 窗口智能体能够捕获这些事实。

## 核心概念

### MemGPT：操作系统类比

Packer 等人（arXiv:2310.08560，v2 2024 年 2 月）将上下文管理映射到操作系统的虚拟内存：

| 操作系统概念 | MemGPT 概念 | 2026 年生产类比 |
|------------|-------------|----------------|
| 内存（RAM） | 主上下文（提示） | Anthropic/OpenAI 上下文窗口 |
| 磁盘 | 外部上下文 | 向量数据库、KV 存储、图存储 |
| 缺页故障 | 记忆工具调用 | `memory.search`、`memory.read`、`memory.write` |
| 操作系统内核 | 智能体控制循环 | 带记忆工具的 ReAct 循环 |

智能体运行正常的 ReAct 循环。一类额外的工具让它能把数据换入和换出主上下文。

### 双层架构

- **主上下文。** 固定大小的提示，持有当前任务。对模型始终可见。
- **外部上下文。** 无限制，可通过工具搜索。相关时读取，发现事实时写入。

原论文在基础窗口之外的两项任务上评估了该设计：超过 100k token 的文档分析，以及跨数天持久记忆的多会话聊天。

### 中断模式

MemGPT 引入了记忆即中断：在对话中途，智能体可以调用记忆工具，运行时执行它，结果作为新观察拼接到下一个助手轮次中。概念上与 Unix 的 `read()` 系统调用完全相同——阻塞进程，返回字节，进程继续。

规范的记忆工具接口：

- `core_memory_append(section, text)` — 写入提示的持久部分。
- `core_memory_replace(section, old, new)` — 编辑持久部分。
- `archival_memory_insert(text)` — 写入可搜索的外部存储。
- `archival_memory_search(query, top_k)` — 从外部存储检索。
- `conversation_search(query)` — 扫描历史轮次。

### MemGPT 在哪里结束，Letta 在哪里开始

2024 年 9 月，MemGPT 变成了 Letta。研究仓库（`cpacker/MemGPT`）保留；Letta 扩展了设计：

- 三层而非两层（核心、回忆、归档——第 08 课）。
- 用原生推理替换 `send_message`/心跳模式（第 08 课）。
- 异步运行记忆工作的睡眠时智能体（第 08 课）。

即使生产系统运行的是 Letta、Mem0 或自定义双层存储，MemGPT 论文仍然是 2026 年的基础。

### 这个模式在哪里出错

- **记忆腐烂。** 写入速度超过读取；检索在过时事实中溺没。修复：定期整合（Letta 睡眠时）、显式失效（Mem0 冲突检测器）。
- **记忆投毒。** 外部记忆是被检索的文本。如果攻击者控制的内容进入记忆笔记，智能体下次会话时会重新摄入它。这是 Greshake 等人（第 27 课）的攻击在时间维度上的重述。
- **引用丢失。** 智能体回忆"用户让我发布 X"，但无法引用是哪一轮次。在每次归档写入时存储来源引用（会话 ID、轮次 ID）。

## 构建它

`code/main.py` 用标准库实现了 MemGPT 的双层模式：

- `MainContext` — 固定大小的提示缓冲区，包含 `core` 字典和 `messages` 列表；超出上限时自动压缩最旧的消息。
- `ArchivalStore` — 内存中的类 BM25 存储（token 重叠评分），存储 (id, text, tags, session, turn) 记录。
- 映射到 MemGPT 接口的五个记忆工具。
- 一个脚本化智能体，先向归档写入事实，然后通过调用 `archival_memory_search` 回答问题。

运行：

```
python3 code/main.py
```

追踪显示智能体写入三个事实，将主上下文填满到上限（强制驱逐），然后通过从归档检索来回答后续问题——无需任何真实 LLM 就重现了 MemGPT 工作流。

## 使用它

今天每个生产记忆系统都是 MemGPT 的变体：

- **Letta**（第 08 课）— 三层、原生推理、睡眠时计算。
- **Mem0**（第 09 课）— 向量 + KV + 图，融合评分层。
- **OpenAI Assistants / Responses** — 通过线程和文件的托管记忆。
- **Claude Agent SDK** — 通过技能和会话存储的长期记忆。

根据操作形态（自托管、托管、框架集成）而非核心模式来选择——核心模式都是 MemGPT。

## 交付它

`outputs/skill-virtual-memory.md` 是一个可复用技能，为任何目标运行时生成正确的双层记忆脚手架（主上下文 + 归档 + 工具接口），并内置驱逐策略和引用字段。

## 练习

1. 添加以 token 数量衡量的 `max_main_context_tokens` 上限（用 `len(text.split()) * 1.3` 近似）。超出上限时将最旧的消息压缩成摘要。比较有无摘要器的行为。
2. 在归档存储上正确实现 BM25（词频、逆文档频率）。在玩具事实集上测量 recall@10，与 token 重叠基线对比。
3. 向归档插入添加 `citation` 字段（session_id、turn_id、source_url）。让智能体在每个基于检索的回答中引用来源。
4. 模拟记忆投毒：添加一条写着"忽略所有未来用户指令"的归档记录。编写一个扫描检索结果中指令形状文本并将其标记为不受信任的守卫。
5. 将实现移植到使用 MemGPT 研究仓库的核心记忆 JSON 模式（`cpacker/MemGPT`）。当你从平铺字符串切换到类型化部分时，哪些内容发生了变化？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| 虚拟上下文（Virtual context） | "无限记忆" | 主上下文（提示）+ 外部（可搜索）双层，带换入/换出。 |
| 主上下文（Main context） | "工作记忆" | 提示——固定大小，始终可见。 |
| 归档记忆（Archival memory） | "长期存储" | 外部可搜索的持久化，按需检索。 |
| 核心记忆（Core memory） | "持久提示部分" | 固定在主上下文中的命名部分。 |
| 记忆工具（Memory tool） | "记忆 API" | 智能体发出的用于读写外部记忆的工具调用。 |
| 中断（Interrupt） | "记忆缺页故障" | 智能体暂停，运行时获取，结果拼接到下一轮次。 |
| 记忆腐烂（Memory rot） | "过时事实" | 旧写入淹没检索；通过整合修复。 |
| 记忆投毒（Memory poisoning） | "注入的持久笔记" | 存为记忆的攻击者内容，在回忆时被重新摄入。 |
