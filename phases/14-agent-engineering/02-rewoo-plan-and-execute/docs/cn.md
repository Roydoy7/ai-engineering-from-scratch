# ReWOO 与规划-执行：解耦规划（ReWOO and Plan-and-Execute: Decoupled Planning）

> ReAct 在单一流中交替进行思考和行动。ReWOO 将它们分离：前期一次性规划，然后执行。token 用量减少 5 倍，HotpotQA 准确率提升 +4%，并且可以将规划器蒸馏到 7B 模型。规划-执行（Plan-and-Execute）对其进行了泛化；规划-行动（Plan-and-Act）将其扩展到网页导航。

**类型：** 构建  
**语言：** Python（标准库）  
**前置知识：** Phase 14 · 01（智能体循环）  
**预计时间：** 约 60 分钟

## 学习目标

- 解释为什么 ReWOO 的规划器/工作器/求解器分离比 ReAct 的交替循环节省 token 并提升鲁棒性。
- 实现一个计划 DAG、按依赖顺序的执行器和一个组合工作器输出的求解器——全部使用标准库。
- 使用 2026 年的"五种工作流模式"框架（Anthropic）决定任务应采用规划-然后-执行还是交替 ReAct。
- 识别何时需要 Plan-and-Act 的合成计划数据用于长序列网页或移动任务。

## 问题所在

ReAct 的交替思考-行动-观察循环简单灵活，但每次工具调用都必须携带完整的先前上下文——包括之前的每一个思考。token 用量随深度呈平方增长。更糟的是：当工具在循环中途失败时，模型必须从错误观察中重新推导整个计划。

ReWOO（Xu 等人，arXiv:2305.18323，2023 年 5 月）注意到了这个问题，并做了一个赌注：前期规划好整件事，并行获取证据，最后组合答案。一次 LLM 调用用于规划，N 次工具调用获取证据（可并行），一次 LLM 调用用于求解。代价是灵活性降低（计划是静态的），换来的是更好的 token 效率和更清晰的故障模式。

## 核心概念

### 三个角色

```
规划器：  user_question -> [plan_dag]
工作器：  [plan_dag]     -> [evidence]        （工具调用，可并行）
求解器：  user_question, plan_dag, evidence -> final_answer
```

规划器生成一个 DAG。每个节点命名一个工具、其参数，以及它依赖的早期节点（引用如 `#E1`、`#E2`）。工作器按拓扑顺序执行节点。求解器将所有内容拼接在一起。

### 为什么少 5 倍 token

ReAct 的提示长度随步骤数线性增长。第 10 步时，提示包含思考 1 加行动 1 加观察 1 加思考 2 加行动 2 加观察 2，如此类推。每个中间步骤还冗余地包含了原始提示。

ReWOO 支付一个规划器提示（较大），N 个小型工作器提示（每个只包含工具调用，无链），以及一个求解器提示。在 HotpotQA 上，论文测量到约 5 倍更少的 token，同时准确率提升 +4 个绝对百分点。

### 为什么更鲁棒

如果 ReAct 中的工作器 3 失败，循环必须在流程中途从错误中推理出来。在 ReWOO 中，工作器 3 返回一个错误字符串；求解器在原始计划的上下文中看到它，可以优雅降级。故障定位是按节点的，而不是按步骤的。

### 规划器蒸馏

论文的第二个结果：因为规划器不看观察，你可以在来自 175B 教师的规划器输出上微调 7B 模型。小模型处理规划；推理时不需要大模型。这现在是标准做法——许多 2026 年的生产智能体使用小规划器和大执行器，或反之。

### 规划-执行（LangChain，2023）

LangChain 团队 2023 年 8 月的博文将 ReWOO 泛化为一种模式名称：规划-执行。前期规划器输出步骤列表，执行器运行每个步骤，可选的重新规划器可以在观察结果后修正。这比 ReWOO 更接近 ReAct（重新规划器将观察带回规划中），但保留了 token 节省。

### 规划-行动（Erdogan 等人，arXiv:2503.09572，ICML 2025）

Plan-and-Act 将该模式扩展到长序列网页和移动智能体。关键贡献是合成计划数据：带标签的轨迹生成器产生计划明确的训练数据。用于微调规划器模型，使其在 WebArena 类任务上能工作超过 30-50 步，而单一 ReAct 轨迹在此处会失去连贯性。

### 何时选择哪种模式

| 模式 | 适用场景 |
|------|----------|
| ReAct | 短任务、未知环境、需要响应式异常处理 |
| ReWOO | 已知工具的结构化任务、token 敏感、证据可并行获取 |
| 规划-执行 | 类似 ReWOO，但在部分执行后需要重新规划 |
| 规划-行动 | 长序列（>30 步）、网页/移动/计算机操作 |
| 思维树 | 搜索值得付出代价时（第 04 课） |

Anthropic 2024 年 12 月的指导：从最简单的开始。如果任务是一次工具调用加摘要，不要构建 ReWOO。如果任务是 40 步的研究任务，不要单独使用 ReAct。

## 构建它

`code/main.py` 实现了一个玩具 ReWOO：

- `Planner` — 一个从提示生成计划 DAG 的脚本化策略。
- `Worker` — 通过注册表分发每个节点的工具调用。
- `Solver` — 读取证据并生成最终答案的脚本化组合器。
- 依赖解析 — 像 `#E1` 这样的引用在分发时被替换为早期工作器的输出。

演示回答"法国首都的人口是多少，精确到百万？"，使用两步计划：（1）查找首都，（2）查找人口，然后求解。

运行：

```
python3 code/main.py
```

追踪首先显示完整计划，然后显示工作器结果，最后是求解器组合。将 token 计数（我们打印一个粗略的字符数）与 ReAct 风格的交替运行进行比较——ReWOO 在这类结构化任务上胜出。

## 使用它

LangGraph 将规划-执行作为配方发布（ReAct 用 `create_react_agent`，规划-执行用自定义图）。CrewAI 的 Flows 直接编码了该模式：你预先定义任务，Flow DAG 执行它们。Plan-and-Act 的合成数据方法仍主要是研究成果；运行时模式（显式计划 DAG）通过 LangGraph 和 CrewAI Flows 在生产中落地。

## 交付它

`outputs/skill-rewoo-planner.md` 根据用户请求和工具目录生成一个 ReWOO 计划 DAG。在移交给执行器之前验证计划（无环、每个引用已解析、每个工具存在）。

## 练习

1. 并行执行独立计划节点的工作器。在一个有 2 个并行组的 6 节点 DAG 上，这能带来什么收益？
2. 添加一个在任何工作器返回错误时触发的重新规划节点。将 ReWOO 转变为规划-执行需要做的最小改动是什么？
3. 用小模型（7B 级）替换 `Planner`，将 `Solver` 保留在前沿模型上。比较端到端质量——分离在哪里失败？
4. 阅读 ReWOO 论文第 4 节关于规划器蒸馏的内容。从概念上重现 175B -> 7B 的结果：你需要什么训练数据，以及如何评估计划质量？
5. 将玩具移植到 Plan-and-Act 的轨迹形式：计划是序列而非 DAG。哪些权衡发生了变化？

## 关键术语

| 术语 | 通俗说法 | 准确含义 |
|------|----------|----------|
| ReWOO | "无观察推理" | 先规划，然后并行获取证据，最后求解——规划提示中不含观察。 |
| 规划-执行（Plan-and-Execute） | "LangChain 的规划-执行模式" | ReWOO 加上执行后可选的重新规划节点。 |
| 规划-行动（Plan-and-Act） | "扩展的规划-执行" | 带合成计划训练数据的显式规划器/执行器分离，用于长序列任务。 |
| 证据引用（Evidence reference） | "#E1, #E2, ..." | 计划节点占位符，在分发时替换为早期工作器输出。 |
| 规划器蒸馏（Planner distillation） | "小规划器，大执行器" | 在大型教师的规划器轨迹上微调小型模型。 |
| Token 效率（Token efficiency） | "更少的往返" | 相比 ReAct 在 HotpotQA 上少用 5 倍 token。 |
| DAG 执行器（DAG executor） | "拓扑分发器" | 按依赖顺序运行计划节点；在每一层并行执行。 |
